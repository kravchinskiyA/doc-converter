# Техническое задание: SaaS-конвертер документов и изображений

**Версия:** 1.37  
**Дата:** 28 октября 2026 г.  
**Статус:** финальная редакция.

## 1. Назначение, этапы и границы

Разработать сервис конвертации документов и изображений с веб-интерфейсом, личным кабинетом, тарифами и API. Пользователь может конвертировать файлы через сайт или API, скачивать результаты и управлять сохранёнными файлами.

**Этап 1:** сайт, регистрация и кабинет, конвертация и OCR, API, подписки и карточная оплата, хранение результатов, локализация и полноценная мобильная работа.

**Этап 2:** Telegram-бот с функциональными правилами раздела 13 и отдельной приёмкой. Наличие бота не входит в условия приёмки первой версии.

Frontend, backend, библиотеки конвертации/OCR, платёжный сервис, инфраструктура и развёртывание описываются в отдельном файле [technology-stack.md](./technology-stack.md). Продуктовые требования определяются настоящим ТЗ. Подготовительные работы перечислены в разделе 15.2.

## 2. Форматы и результаты конвертации

| Вход | Выход | Требуемое поведение |
| --- | --- | --- |
| PDF | DOCX | Редактируемый текст, включая распознавание сканов посредством OCR |
| DOCX | PDF | Конвертация документа с сохранением структуры по критериям раздела 2.4 |
| JPG/JPEG | PDF | Отдельный PDF для изображения либо объединение набора по настройке |
| PNG | PDF | То же; прозрачные области заменяются белым фоном |
| WEBP | PDF | То же для статического WEBP; анимированный WEBP отклоняется |
| PDF | JPG | Одностраничный PDF без выбора страниц; для многостраничного — выбор по миниатюрам |
| PDF | WEBP | Те же правила выбора страниц |

PDF с паролем отклоняется с понятным сообщением. Ввод пароля и снятие защиты не предусмотрены. Повреждённые файлы и неподдерживаемые направления не конвертируются.

На сайте и через API **принимаются `.jpg` и `.jpeg` без учёта регистра расширения**, включая `.JPG` и `.JPEG`. К ним применяются одинаковые ограничения размера, счётчики изображений и правила объединения в PDF. Это варианты расширения одного входного формата, а не отдельные направления конвертации. Для PDF → JPG выходные изображения сохраняются с расширением **`.jpg`**. Другие направления не входят в перечень поддерживаемых направлений.

### 2.1. Изображения → PDF

В форме находится чекбокс **«Объединить изображения в один PDF»**, по умолчанию выключенный.

- Выключен: одно изображение преобразуется в один отдельный PDF.
- Включён: выбранные изображения объединяются в один PDF.
- JPG/JPEG, PNG и WEBP можно смешивать в одном наборе для этого направления.
- Перед объединением пользователь может менять порядок изображений перетаскиванием на сайте; в боте второго этапа — кнопками перемещения по разделу 13. В итоговом PDF сохраняется выбранный относительный порядок исправных изображений.
- При ошибке одного изображения PDF формируется из остальных исправных изображений; ошибочный файл выделяется с причиной. Если исправных файлов нет, успешный пустой PDF не создаётся.
- Объединение не увеличивает допустимое число входных файлов и не превращает несколько успешно обработанных изображений в одну использованную попытку.

**Каждое исправное входное изображение размещается на одной странице A4.** Для горизонтального изображения ориентация страницы альбомная, для вертикального или квадратного — книжная. Ориентация выбирается автоматически отдельно для каждого изображения, в том числе при объединении: в одном PDF могут быть страницы обеих ориентаций.

Поля — **10 мм со всех сторон**. Изображение центрируется в оставшейся области и масштабируется до вписывания с сохранением пропорций: большие изображения уменьшаются, маленькие увеличиваются. Обрезки и растягивания с изменением пропорций нет. Размер A4, поля, размещение и автоматическая ориентация фиксированы для первой версии; отдельные пользовательские настройки не добавляются. Правила одинаковы для сайта и API.

При PNG/WEBP → PDF прозрачные области заменяются **белым фоном**. Переключателя сохранения прозрачности в первой версии нет.

### 2.2. PDF → изображения

Если в PDF одна страница, преобразование выполняется без отдельного шага выбора страниц. Если страниц несколько, на сайте пользователь видит миниатюры и может выбрать конкретные страницы. Изначально выбраны все страницы. Для бота второго этапа предусмотрен текстовый выбор номеров/диапазонов по разделу 13.3; правило миниатюр относится к сайту.

Для PDF → JPG и PDF → WEBP предусмотрены ручные настройки:

| Параметр | Допустимые значения | По умолчанию |
| --- | --- | --- |
| Разрешение растрирования | 72, 150 или 300 DPI | 150 DPI |
| Качество сжатия | Шкала от 1 до 100, ползунок на сайте | 85 |

Разрешение определяет число пикселей выходного изображения при преобразовании страницы PDF. Качество — условная шкала настройки сжатия, а не процент сохранённой информации; более высокое значение означает меньше потерь и обычно больший файл.

**Одна пара настроек применяется ко всем файлам и выбранным страницам одной операции.** Индивидуальных настроек для отдельных страниц или файлов в первой версии нет. На сайте и через API действуют одинаковые допустимые значения и значения по умолчанию. Если параметр не передан, используется его значение по умолчанию. Значения вне установленного набора/диапазона отклоняются при валидации с объяснением допустимых значений. Пиксельные ограничения указаны в разделе 3.4; отдельного лимита страниц нет по разделу 3.5. Ограничения распаковки, результата, времени, памяти, параллельности и частоты запросов указаны в разделах 3.6–3.8.

При PDF → JPG/WEBP изображения формируются **на белом фоне**, без пользовательского переключателя сохранения прозрачности. Это правило не меняет исходные размер и ориентацию страниц PDF: A4 и поля 10 мм из раздела 2.1 применяются к направлению «Изображения → PDF».

### 2.3. OCR

Обязательные языки первой версии: **русский, украинский, английский, французский, немецкий, польский**. Язык определяется автоматически. Поддерживается один или несколько этих языков в одном документе; обычный сценарий — одноязычный документ. После первой версии добавляются испанский, итальянский и португальский по разделу 2.5.

OCR требуется для PDF → DOCX, чтобы результат содержал **редактируемый печатный текст**. Рукописный OCR относится к следующему этапу по разделу 2.5 и не входит в приёмку первой версии.

**Контрольный набор готовит разработчик, пользователь утверждает его перед приёмкой.** В набор входят документы на каждом из шести обязательных языков и документы со смешанными языками. Для проверки OCR подготавливаются чёткие сканы печатного текста и эталонная расшифровка каждого документа. Для проверки конвертации и вёрстки набор также содержит PDF с текстовым слоем и DOCX с проверяемыми элементами структуры по разделу 2.4. Файлы и эталонные результаты фиксируются в утверждённом контрольном наборе.

Для чётких сканов печатного текста **в каждом утверждённом контрольном документе допускается не более 2% символьных ошибок OCR**, без учёта различий пробелов и переносов строк. Ошибки — замены, пропуски и лишние символы. При расчёте пробелы и переносы строк исключаются из сравнения; сравниваются остальные символы эталонного и распознанного текста. Результат одного документа не компенсируется более точным результатом другого.

Метрика: `CER = (S + D + I) / N × 100%`, где `S` — число замен, `D` — пропусков, `I` — лишних символов при сопоставлении с эталоном, `N` — число символов эталона после указанного исключения пробелов/переносов. Основание определения метрики: [CER — Hugging Face Evaluate](https://github.com/huggingface/evaluate/blob/main/metrics/cer/cer.py). Предельный CER для контрольного набора — 2%.

Этот порог относится к утверждённому контрольному набору чётких сканов, а не ко всем возможным загружаемым документам. Нечёткие фотографии проверяются отдельно на утверждённых контрольных примерах; тот же числовой порог им автоматически не назначается. Дополнительные языки и рукописный OCR описаны в разделе 2.5.

### 2.4. Сохранение вёрстки PDF ↔ DOCX

При PDF → DOCX и DOCX → PDF требуется сохранять порядок текста, абзацы, заголовки, списки, изображения и структуру простых таблиц. Для OCR дополнительно действуют требования к редактируемому печатному тексту и допустимым символьным ошибкам по разделу 2.3.

Допускаются замена шрифта похожим, небольшие смещения элементов и изменение переносов строк/страниц. Пропавшие страницы, целые абзацы или изображения считаются дефектом; допустимый процент символьных ошибок OCR не разрешает такую потерю содержимого.

Сложные формулы, многоколоночные макеты и сложные таблицы проверяются отдельно на утверждённых контрольных примерах. Разработчик включает соответствующие примеры и ожидаемые результаты в контрольный набор для утверждения пользователем перед приёмкой.

### 2.5. Расширения OCR после первой версии

**Печатный текст:** добавить **испанский, итальянский и португальский**, сохранив автоматическое определение языка и поддержку смешанных документов. Вместе с шестью исходными языками это девять языков печатного OCR. При подключении новых языков контрольный набор дополняется чёткими печатными документами и смешанными примерами; к ним применяются критерии печатного OCR раздела 2.3. Расширение не меняет три языка интерфейса сайта/бота.

**Рукописный текст:** на следующем этапе добавить распознавание **разборчивого рукописного текста в PDF → DOCX**, первоначально на **украинском, русском и английском**. В одном документе могут сочетаться печатный и рукописный текст; результат должен содержать редактируемый текст. Другие рукописные языки автоматически не включаются.

Для рукописи разработчик готовит отдельные контрольные образцы с эталонной расшифровкой; конкретные критерии качества и допустимые ошибки согласуются на этих образцах до приёмки расширения. Порог **CER 2% печатного OCR к рукописи автоматически не применяется**. Гарантия распознавания произвольного неразборчивого почерка не предоставляется. Конвертация и OCR по-прежнему выполняются в нашем окружении по разделу 12.3.

Оба расширения находятся за пределами первой версии и проходят отдельную приёмку.

### 3.4. Пиксельные ограничения и размер пакета

Для всех фиксированных тарифов, включая гостевой режим, одно входное изображение и одно изображение, создаваемое из PDF, должны одновременно соответствовать двум ограничениям:

- площадь — **не более 40 мегапикселей**, то есть `ширина × высота ≤ 40 000 000 пикселей`;
- каждая сторона — **не более 12 000 пикселей**.

Размер в пикселях проверяется дополнительно к тарифному размеру в байтах. Для PDF → JPG/WEBP учитывается размер выходного изображения при выбранном DPI. При превышении сервер объясняет причину и предлагает выбрать меньшее разрешение из установленных вариантов; автоматически выбранное качество или разрешение не изменяются. Для входного изображения превышение означает отказ с объяснением ограничения. Применяются общие правила ошибки файла и сохранения обработки остальных допустимых файлов пакета по разделу 8.2.

Суммарный размер входных файлов одной операции:

| Контекст | Документы | Изображения |
| --- | --- | --- |
| Гость и базовый тариф | Один PDF до 2 МБ либо один DOCX до 5 МБ | Одно изображение до 2 МБ |
| Pro, до 5 файлов | До 150 МБ | До 125 МБ |
| Максимальный, до 5 файлов | До 500 МБ | До 250 МБ |
| Enterprise | По договорённости | По договорённости |

Для каждого файла одновременно действует его индивидуальный предел по разделу 3.3. Сумма относится к содержимому входных файлов; технические накладные данные запроса не уменьшают установленный допустимый объём файлов. Один пакет по-прежнему содержит одно направление конвертации. Пиксельные ограничения и размеры пакета одинаковы для сайта и API.

### 3.5. Обработка без отдельного лимита страниц

**Отдельный продуктовый лимит количества страниц документа не устанавливается.** Допуск файла определяется установленными ограничениями размера и содержимого; обработка дополнительно ограничивается временем, памятью и размером результата. Пределы времени и результата указаны в разделе 3.6, памяти — в разделе 3.7.

При PDF → JPG/WEBP преобразуются только выбранные пользователем страницы. Большое общее количество страниц само по себе не является причиной отказа, если пользователь выбрал допустимые для обработки страницы и соблюдаются технические пределы. При PDF → DOCX обрабатывается документ в рамках того же подхода без отдельного тарифного лимита страниц.

Если при обработке превышен технический предел, обработка соответствующего файла завершается понятной ошибкой с указанием причины; попытка за неуспешную конвертацию не списывается. Отказ может возникнуть уже во время обработки, а не только при загрузке. Правила продолжения обработки остальных файлов пакета сохраняются. Отсутствие лимита страниц не означает неограниченное время, память или объём результата.

### 3.6. Распаковка DOCX, размер результата и время

Следующие технические пределы одинаковы для гостя и всех фиксированных тарифов, на сайте и через API:

| Параметр | Предел |
| --- | --- |
| Суммарный объём содержимого одного DOCX после распаковки | 500 МБ |
| Количество внутренних файлов одного DOCX | 10 000 |
| Суммарный объём готовых результатов одного исходного файла | 500 МБ |
| Активная обработка одного исходного файла, включая OCR | 10 минут |

Пределы распаковки DOCX действуют дополнительно к тарифному размеру загружаемого файла и проверяются по фактическому распаковываемому содержимому. Превышение объёма либо количества внутренних файлов останавливает обработку соответствующего DOCX с понятной причиной.

Для PDF → JPG/WEBP в предел результата 500 МБ входит **сумма изображений всех выбранных страниц одного PDF**. Для объединения изображений в PDF действует предел **500 МБ на один итоговый PDF**. Временный ZIP не входит в этот предел и по-прежнему не учитывается повторно в хранилище. Предел результата не отменяет установленное сохранение принятого результата сверх остатка квоты хранилища по разделу 10.3.

Предел 10 минут отсчитывается от начала активной серверной обработки файла, включая OCR. Загрузка входных файлов, ожидание очереди и скачивание в него не входят. В обычном пакете предел применяется к каждому исходному файлу отдельно, а не к пакету суммарно. При объединении изображений **10 минут даются на создание всего итогового PDF**.

При превышении любого указанного предела соответствующая конвертация завершается ошибкой с объяснением причины и **не расходует попытку**. При неуспешном создании объединённого PDF попытки его входных изображений за эту неуспешную конвертацию не списываются. Остальные независимые допустимые файлы пакета продолжают обрабатываться; автоматического повтора нет.

### 3.7. Память, параллельная обработка и очередь

На обработку одного исходного файла выделяется **не более 2 ГБ оперативной памяти**, включая OCR и вспомогательные процессы этой конвертации. При объединении изображений предел 2 ГБ относится к созданию всего итогового PDF, а не предоставляется отдельно каждому изображению. Предел одинаков для гостя и всех фиксированных тарифов. При превышении соответствующая конвертация завершается понятной ошибкой без списания попытки; остальные независимые файлы продолжают обрабатываться.

| Контекст | Одновременно в обработке | Дополнительно в очереди |
| --- | --- | --- |
| Гость, неподтверждённый аккаунт, базовый тариф | 1 задача | До 5 задач |
| Pro | До 2 задач | До 5 задач |
| Максимальный | До 3 задач | До 5 задач |
| Enterprise | По договорённости | По договорённости |

Обычно одна задача — обработка одного исходного файла. **Объединение нескольких изображений в один PDF считается одной задачей** для памяти, параллельности и очереди. При этом число успешных попыток изображений по-прежнему равно числу успешно объединённых входных изображений. Пакет без объединения создаёт отдельные задачи для исходных файлов.

Сайт, API, все вкладки и устройства используют общие ограничения владельца: аккаунта, в том числе неподтверждённого, либо гостевого идентификатора. Замена API-ключа не создаёт отдельную очередь или дополнительные места обработки.

Приём нового пакета учитывает валидацию и остаток квоты: сначала определяются файлы, допускаемые по установленным правилам частичного допуска. Если все требуемые для них задачи не помещаются в свободные места обработки и очереди, **новый запрос отклоняется целиком без списания попыток** с объяснением нехватки мест. Автоматического приёма части пакета только по вместимости очереди нет. Проверка и занятие мест выполняются согласованно на сервере, чтобы параллельные запросы не превышали пределы.

Принятые задачи ожидают освобождения места и затем начинают обработку без повторной загрузки файлов. Ожидание очереди не входит в предел 10 минут активной обработки. Списание попыток происходит только после успеха, а необходимые остатки квоты согласованно резервируются на время принятых задач. Это не автоматическая повторная отправка неуспешной конвертации. Уже принятые задания не отменяются пользователем; специальная системная остановка при удалении аккаунта выполняется по разделу 6.4.

Общие пределы первой версии — 5 активных задач и 100 дополнительных задач в общей очереди — указаны в разделе 12.8. Индивидуальные пределы выше не означают гарантированное одновременное выделение всех мест каждому пользователю. Инфраструктура подбирается под установленную нагрузку и описывается в отдельном файле technology-stack.md.

### 3.8. Частота запросов

Для гостевого режима и всех фиксированных тарифов действуют одинаковые технические пределы:

| Вид запроса | Предел на аккаунт или гостевой идентификатор |
| --- | --- |
| Создание заданий | 10 запросов в минуту |
| Проверка состояния заданий | 120 запросов в минуту суммарно |
| Проверка состояния одного задания | Не чаще одного раза в 5 секунд |
| Скачивание результатов | 10 запросов в минуту |

Лимиты создания, проверки состояния и скачивания учитываются раздельно. Для проверки состояния одновременно действуют общий минутный предел и интервал конкретного задания. Создание пакета считается одним запросом создания, при этом число файлов, очередь и квоты проверяются дополнительно. Повторное скачивание также является запросом скачивания.

Сайт и API используют общие технические счётчики аккаунта или гостя; новые вкладки, устройства вошедшего пользователя и замена ключа не предоставляют дополнительные пределы. Технический предел запросов не является количеством успешных конвертаций и не меняет правила расхода попыток.

При превышении запрос отклоняется с объяснением ограничения и временем, через которое его можно повторить. Отклонённый запрос не запускает новую обработку и не списывает попытку; уже принятые задания продолжаются. Автоматической повторной отправки файлов нет. Дополнительная защита по IP и ограничения рассылки/входа заданы в разделах 12.12–12.13; общей продуктовой квоты 5/5 на IP не вводится.

## 4. Правила счётчиков и блокировок

1. Документы и изображения учитываются **раздельно**. На максимальном тарифе это 100 документов и отдельно 100 изображений, не 100 суммарно.
2. Попытка списывается только после успешной конвертации входного файла. Ошибки загрузки, проверки и обработки её не расходуют.
3. Один PDF на 20 страниц, преобразованный в изображения, расходует **одну документную попытку**, независимо от количества выходных файлов.
4. Пять успешно обработанных изображений расходуют пять попыток изображений, даже при объединении в один PDF.
5. Сайт и API используют **общие счётчики аккаунта**. Смена канала не даёт дополнительную квоту.
6. Таймер запускается **от исчерпания лимита**, а не от первой операции. Гостю после пятого успеха категории — 12 часов, базовому аккаунту — 5 часов; Pro после 30 и максимальному после 100 — 2 часа.
7. Блокируется только новая конвертация исчерпанной категории. Вторая категория доступна, пока не исчерпан её собственный лимит. Таймеры независимы; после окончания восстанавливается полный лимит категории.
8. Уже принятые задания продолжаются, готовые результаты доступны для скачивания. Скачивание и построение миниатюр не являются новыми успешными конвертациями. Специальное правило остановки заданий и прекращения доступа при удалении аккаунта задано в разделе 6.4.
9. Квоты Pro/максимального не являются месячными/годовыми: действует цикл «порог → двухчасовая блокировка → восстановление». Годовая оплата не умножает пороги на 12.

Пример: Pro исчерпал документы в 10:20, изображения в 11:10. Документы снова доступны в 12:20, изображения в 13:10.

### 4.1. Переход между режимами и тарифами

- При регистрации текущий гостевой расход переносится в новый неподтверждённый аккаунт; далее счётчики учитываются по аккаунту во всех браузерах. До подтверждения сохраняются гостевые пороги 5 документов и 5 изображений и блокировки категории на 12 часов от исчерпания. Уже начавшийся таймер переносится с исходным сроком окончания, а не запускается заново.
- Именно после подтверждения email нового аккаунта предоставляются полные **5 документов и 5 изображений** базового тарифа. Гостевой расход и гостевая блокировка не переносятся в подтверждённый режим: после трёх гостевых документов до подтверждения остаются две попытки, а после подтверждения — пять. Для последующего исчерпания действует базовый таймер 5 часов.
- Обычный выход/повторный вход в существующий подтверждённый аккаунт не создаёт новый лимит.
- При фактическом повышении базовый → Pro/максимальный или Pro → максимальный счётчики расхода сбрасываются и **обе активные блокировки снимаются**. Предоставляются полные лимиты нового тарифа. Pro с расходом 20 документов → максимальный получает 100 документных попыток, не 80. Изменение применяется после подтверждённой успешной оплаты, не при открытии платёжной страницы.
- При фактическом понижении для каждой категории переносится число успешных входных файлов **текущего цикла на момент перехода**. Если оно меньше нового порога, остаток равен новому порогу минус расход; если достигло/превысило порог, с момента перехода запускается полная блокировка новой категории: **2 часа для Pro, 5 часов для подтверждённого базового**. Старый срок блокировки заменяется этим сроком. Например, максимальный с расходом 40 документов → Pro: документы блокируются на 2 часа; Pro с расходом 7 документов и 2 изображений → базовый: документы блокируются на 5 часов, остаются 3 попытки изображений. Категории независимы; после блока расход категории сбрасывается обычным образом.
- Те же правила понижения действуют при немедленной отмене платной подписки, окончании оплаченного срока с выключенным автопродлением и окончании неоплаченных льготных суток. В пределах установленных льготных суток сохраняется прежний тариф; преждевременного перехода на базовый нет.
- Продление прежнего тарифа, включение/выключение автопродления, смена месяца на год или года на месяц **без смены уровня тарифа** не сбрасывают счётчики, резервы и сроки блокировок. Повторное платёжное уведомление также ничего не сбрасывает.
- События успешной конвертации и смены тарифа обрабатываются последовательно на сервере: один успех относится ровно к одному циклу. При задержанном уведомлении о своевременном действительном продлении восстанавливается непрерывность прежнего тарифа с учётом реально прошедшего времени и уникальных успешных операций; технический промежуточный переход на базовый не создаёт дополнительной полной квоты. Устаревшие платежи обрабатываются по разделу 11.11 и не восстанавливают прежние права.

Проверять и резервировать остаток согласованно для параллельных запросов сайта/API. Резерв не является списанием и не запускает таймер; ошибка освобождает резерв, успех превращает его в списание. Один серверный успех не должен списываться дважды из-за повторной обработки уведомления.

### 4.2. Идентификация гостя и защита лимитов

Гость определяется **случайным идентификатором в защищённом cookie браузера**. Счётчики успешных документов/изображений и сроки блокировок хранятся и проверяются на сервере. Новые вкладки, перезапуск браузера и смена сети не обнуляют попытки и таймеры, пока cookie сохранён. Cookie должен обеспечивать установленный возврат к результатам после повторного открытия браузера.

Необходимые cookie обязательны для гостевой конвертации. Если их сохранение запрещено, сайт объясняет причину недоступности гостевой конвертации и предлагает включить необходимые cookie; обход проверки без cookie не предоставляется.

После очистки cookie, в другом браузере либо в отдельной среде инкогнито новый браузерный идентификатор получает собственные **5 документов и 5 изображений**. Это отдельные гостевые счётчики; старые счётчики на сервере не обнуляются. Утрата идентификатора прекращает доступ к прежним гостевым заданиям и результатам по правилам раздела 10.1.

**Общей продуктовой квоты 5/5 на IP нет:** гости с разными идентификаторами в одной сети не расходуют единый лимит. IP используется для дополнительной защиты от массовых запросов; дополнительные пороги и меры защиты заданы в разделах 12.12–12.13. IP не предоставляет доступа к заданиям или файлам другого гостя.

Установленный механизм допускает получение новой гостевой квоты сменой браузера или очисткой cookie. Гарантированное определение одного человека во всех таких средах не является требованием этой версии. Для вошедшего неподтверждённого аккаунта смена браузера или очистка cookie не сбрасывает его серверные счётчики: после входа применяются ограничения аккаунта по разделу 4.1.

### 4.3. Принятые задания при изменении тарифа

При допуске задания сервер фиксирует владельца, категорию, цикл квоты, резервы и применённые ограничения входных файлов/пакета. Повышение, понижение, отмена или окончание подписки **не отменяют уже принятые задания и не проверяют их размер/пакет заново по новому тарифу**. Например, принятые на максимальном тарифе пять PDF по 100 МБ завершаются и после перехода на базовый. Системная остановка при удалении аккаунта остаётся исключением.

- При реальной смене уровня тарифа создаётся новый цикл учёта по правилам раздела 4.1. Незавершённые задания сохраняют резервы прежнего цикла: успех учитывается в нём однократно, ошибка освобождает его резерв. Эти поздние успехи не уменьшают квоту нового цикла и не запускают в нём блокировку. При понижении в новый цикл переносится только расход, уже успешно накопленный к моменту перехода, без незавершённых резервов.
- Если уровень тарифа не изменился, цикл не меняется: продление или смена месяца/года не освобождают существующие резервы. При обычном восстановлении квоты после блока начинается новый цикл соответствующей категории; старый цикл не может повторно сбросить новый.
- Выполняющиеся задачи продолжаются с уже предоставленным ресурсом. Задачи очереди запускаются по новой допустимой параллельности аккаунта и общему пределу сервиса. Если после понижения уже работают три задачи при новом пределе один, они завершаются; следующая не запускается, пока активных задач не станет меньше одного. Все старые и новые задачи учитываются в общей занятости аккаунта; смена тарифа не даёт отдельной очереди.
- Результаты принятых задач сохраняются в кабинете на 6 календарных месяцев от готовности. Даже если новый объём хранилища уже превышен, эти результаты сохраняются по правилу принятого пакета; новые операции блокируются до освобождения места. Смена тарифа не продлевает сроки ранее сохранённых файлов.
- Новые запросы сразу проверяются по актуальным тарифу, остаткам, блокировкам, хранилищу и очереди. На сайте/API показываются действующие остатки и время окончания блока; старый результат не выдаётся за расход новой квоты.

**Контрольные примеры:** Pro с 29 успехами и одним принятым документом повышается до максимального: получает 100 новых попыток, завершение старого документа оставляет 100. Максимальный с 40 успехами и двумя принятыми документами понижается до Pro: получает блок документов на 2 часа от перехода; два поздних успеха старого цикла не перезапускают этот срок. Простой повтор уведомления об оплате не выполняет ни один переход повторно.

## 5. Страницы, локализация и мобильная работа

## 6. Регистрация и управление аккаунтом

### 6.1. Почтовые коды

Для регистрации достаточно **email и пароля**. Имя/фамилия добавляются добровольно в профиле. Почта подтверждается вводом кода из письма, не переходом по ссылке.

**Пароль:** от **8 до 128 символов** включительно. Разрешены пробелы, кириллица и символы других языков. Обязательных сочетаний цифр, заглавных букв и специальных символов нет. Распространённые и известные скомпрометированные пароли отклоняются с понятным объяснением необходимости выбрать другой пароль. Разрешены вставка из буфера, автозаполнение и менеджеры паролей. Правила одинаковы при регистрации, смене и восстановлении пароля; пароль не обрезается до допустимой длины.

**Повторная регистрация занятого email:** второй аккаунт не создаётся, пароль существующего аккаунта не меняется. Для корректно заполненной формы на странице показывается одинаковое сообщение для нового и уже занятого email: «Проверьте почту для продолжения. Если аккаунт уже существует, войдите или восстановите пароль». Для нового аккаунта отправляется код подтверждения регистрации; для существующего — письмо с пояснением, как войти или восстановить доступ. Сам факт повторной регистрации не подтверждает email и не предоставляет доступ к существующему аккаунту. Дополнительные ограничения отправки писем заданы в разделах 12.12–12.13.

| Параметр кода | Значение |
| --- | --- |
| Формат | 6 цифр |
| Срок действия | 10 минут от отправки |
| Попытки ввода | Максимум 5 для выданного кода |
| Повторная отправка | Не чаще одного раза в минуту |

Эти параметры действуют для описанных почтовых подтверждений, включая каждый из двух кодов смены email. Неверный, истёкший или исчерпавший попытки код не подтверждает действие.

Коды одноразовые, привязаны к аккаунту и конкретной операции, проверяются на сервере и не записываются в журналы. Код смены email не подтверждает удаление аккаунта или смену пароля. Дополнительные ограничения рассылки и входа по паролю заданы в разделах 12.12–12.13.

### 6.2. Смена email

1. Пользователь инициирует смену; первый код отправляется на **старую текущую почту**.
2. После успешного ввода первого кода второй отправляется на **новую почту**.
3. Email меняется **только после успешного ввода обоих кодов**. Без любого из них адрес остаётся прежним.
4. Пользователь выбирает, завершить ли все сессии и отключить API-ключ после успешной смены или оставить их действующими. Чекбокс **«Выйти на всех устройствах и отключить API-ключ после смены email» включён по умолчанию**; пользователь может его выключить.

Если чекбокс включён, **после успешной смены** завершаются все сессии, включая текущую, и отключается API-ключ. Пользователь входит заново с новым email; пароль при смене email не меняется. Новый ключ выпускается вручную по правилам раздела 7, после завершения текущих конвертаций. Если чекбокс выключен, сессии и ключ сохраняются. Незавершённая или отклонённая смена email сама по себе не применяет выбранное завершение сессий и отключение ключа. Уже принятые задания не отменяются.

**Общий срок операции — 20 минут с отправки первого кода на старую почту.** Каждый код действует 10 минут от его отправки по разделу 6.1; повторная отправка не продлевает общий срок операции. Оба подтверждения должны быть завершены до истечения этих 20 минут. По истечении срока адрес остаётся прежним, подтверждения этой операции больше не применяются; для новой попытки нужно заново пройти оба шага.

Если новый email занят другим аккаунтом, смена отклоняется с сообщением **«Этот адрес недоступен для смены почты. Укажите другой»**. Аккаунты не объединяются, текущий email сохраняется. Доступность нового адреса проверяется перед отправкой кодов и повторно перед окончательным изменением. Если к моменту завершения адрес уже занят, смена не применяется даже при успешно введённых кодах.

Связывать оба подтверждения с одним запросом и конкретными адресами, не применять первый код как завершённую смену; изменение нового адреса отменяет подтверждения прежнего запроса.

### 6.3. Смена и восстановление пароля

Смена пароля подтверждается кодом на текущий email. Без кода новый пароль не применяется.

При забытом пароле пользователь вводит email, получает код на текущую почту, подтверждает его и задаёт новый пароль. После успешной смены/восстановления:

- завершаются сессии **на всех устройствах, включая текущее**;
- действующий API-ключ отключается; новые запросы с ним не авторизуются;
- уже принятые API-задания продолжаются, результаты сохраняются в кабинете;
- вход выполняется с новым паролем; новый ключ выпускается вручную после завершения текущих конвертаций.

При потере доступа к почте используется резервный код по разделу 6.5. Если действующего резервного кода нет, пользователь обращается в поддержку; восстановление без проверяемого подтверждения владения не гарантируется. Обычное восстановление пароля по коду на текущий email сохраняется.

### 6.4. Удаление аккаунта

Удаление доступно только после кода на email аккаунта. Без подтверждения аккаунт и файлы не удаляются. После подтверждённого удаления удаляются аккаунт и связанные сохранённые файлы.

При удалении аккаунта активная подписка **прекращается**, автопродление и будущие списания прекращаются. **Возврат за оставшийся оплаченный срок при удалении аккаунта не создаётся.** Это отдельное правило удаления аккаунта; самостоятельная отмена подписки по разделу 11.2 сохраняет установленный возврат за неиспользованный срок.

Перед подтверждением удаления пользователю явно сообщается, что аккаунт и файлы будут удалены, платный доступ прекратится и остаток оплаты из-за удаления аккаунта не возвращается. Подтверждение по почтовому коду по-прежнему обязательно.

**Сразу после подтверждения удаления** прекращается доступ к аккаунту, завершаются все сессии и отключается API-ключ. Ожидающие задания удаляются из очереди, текущая обработка системно останавливается. Её результаты не сохраняются и не публикуются в удалённом аккаунте. Завершение обработки одновременно с удалением не должно создавать аккаунт или возвращать ему файлы.

Это специальное правило удаления аккаунта: обычная отмена конвертации пользователем по-прежнему не предоставляется. Сроки физической очистки файлов заданы в разделе 10.4; резервные копии регулируются разделом 10.5, уведомления о возврате после удаления и ограниченная служебная контактная запись заданы в разделе 11.13. Уже начатый возврат не должен выполняться повторно из-за повторной обработки удаления.

### 6.5. Восстановление при потере доступа к почте

**Подготовка:** после подтверждения email пользователю предлагается сохранить **10 одноразовых резервных кодов**. Сохранение не является новым обязательным полем регистрации. Набор можно выпустить или заменить в кабинете после подтверждения кодом на текущую почту; при замене старый набор полностью отключается. Пользователь заранее предупреждается, что при утрате почты и резервных кодов восстановление может оказаться невозможным.

Резервные коды — отдельные непредсказуемые секреты, а не шестизначные почтовые коды. Они показываются один раз и хранятся на сервере только в виде необратимых проверочных значений; не попадают в журналы, письма, ответы API и служебную панель. Пользователь хранит их отдельно от потерянной почты. Служебные резервные коды сотрудников из раздела 12.19 не подходят для пользовательского аккаунта.

**Самостоятельное восстановление:**

1. На странице входа пользователь выбирает «Нет доступа к почте», указывает прежний email и действующий резервный код.
2. После проверки кода указывает новый свободный email и подтверждает его почтовым кодом по разделу 6.1. Проверка доступности адреса повторяется перед применением смены; чужие аккаунты не объединяются.
3. Задаёт новый пароль по действующим правилам. Только после успешного подтверждения новой почты и пароля изменения применяются вместе. Незавершённая операция не меняет email, пароль, сессии и API-ключ; один резервный код не может завершить две операции.
4. При успехе использованный резервный код и остаток прежнего набора отключаются, завершаются все сессии и действующие запросы смены/восстановления учётных данных, отключается API-ключ и прежняя привязка бота. Уведомления отправляются на прежний и новый адреса без секретов. Автоматического входа нет: пользователь входит с новым email/паролем и получает возможность выпустить новый набор резервных кодов.

Это **специальный сценарий восстановления**, в котором резервный код заменяет подтверждение старой почты. Он не отменяет обычное требование двух почтовых подтверждений при смене email по разделу 6.2. Неверные коды не изменяют аккаунт; запросы и проверки защищаются от перебора с ограничением частоты, без раскрытия существования аккаунта. Ограничение попыток восстановления не блокирует само по себе действующие входы владельца. Почтовый код и его срок — по разделу 6.1; резервный код действует до использования, отзыва набора или удаления аккаунта. Начатый запрос восстановления ограничивается 20 минутами от проверки резервного кода, без продления при повторной отправке письма.

Для проверки резервных кодов допускается не более 5 неверных попыток на аккаунт за 15 минут; затем только этот способ проверки приостанавливается на 15 минут. Почтовые и общие ограничения по IP сохраняются. Отзыв и использование кодов учитываются так, чтобы восстановление резервной копии не делало старый код снова действующим.

Подписка, платежи, файлы, исходные сроки хранения, расход и блокировки квот сохраняются; восстановление не выдаёт новую квоту. Принятые конвертации продолжаются и сохраняются по общим правилам. API-ключ после восстановления пользователь выпускает вручную после окончания текущих заданий.

**Если резервного кода нет:** пользователь обращается в поддержку. Обращение не предоставляет доступ к аккаунту и не позволяет автоматически изменить почту. Одного чека оплаты недостаточно для подтверждения владения; секреты и содержимое файлов поддержке не передаются, произвольный доступ сотруднику не предоставляется. Подробный регламент ручного восстановления находится за пределами настоящего ТЗ.

Основание защитных механизмов: [OWASP — восстановление пароля и доступа](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).

## 7. API-ключ пользователя

- Ключ один, доступен для просмотра/копирования и замены. До первого выпуска ключа нет: пользователь создаёт его **по собственному запросу в кабинете**.
- Замена требует кода на текущую почту. Без кода она не выполняется; после успешной замены старый ключ **немедленно недействителен**.
- Смена пароля отключает ключ; после неё новый также создаётся вручную, как первый.
- Пока текущие конвертации не завершены, **генерация/замена ключа запрещена**. Ограничение проверяется сервером, а не только отключённой кнопкой.
- После успешной смены email сохранение ключа/сессий зависит от выбора пользователя; завершение всех сессий и отключение ключа включены по умолчанию по разделу 6.2. Автоматический выпуск нового ключа не выполняется.
- Отключение ключа при смене пароля не отменяет уже принятые API-задания.

Скрывать значение по умолчанию, защищать хранение с учётом повторного раскрытия, генерировать непредсказуемый ключ, исключить его из URL/журналов и предотвращать несколько действующих ключей при конкурентной замене.

## 8. Обработка файлов, ошибки и продолжение работы

### 8.1. Валидация

Предварительные проверки интерфейса дополняются обязательной серверной проверкой в предлагаемом механизме. Нельзя доверять только имени, расширению или присланному MIME-типу.

| Причина отказа | Поведение |
| --- | --- |
| Файла нет или он пуст | Попросить корректный файл, не конвертировать |
| Тип/направление не поддерживается или содержимое не соответствует типу | Показать причину и допустимые форматы |
| Превышен размер/число файлов/защитный лимит | Указать конкретный лимит |
| Файл повреждён/не читается | Выделить файл, объяснить отказ, остальные допущенные файлы продолжаются |
| Антивирус обнаружил угрозу либо не смог завершить проверку | Не создавать миниатюры, не конвертировать и не выполнять OCR для этого файла; показать понятную причину, попытку не списывать. Остальные допустимые файлы продолжают обрабатываться |
| PDF с паролем или анимированный WEBP | Отклонить конкретный файл без списания |
| PDF — скан | Сам по себе не является причиной отказа; PDF → DOCX использует OCR |
| Недопустимые страницы/настройки | Не запускать соответствующую обработку, объяснить исправление |
| Категория заблокирована | Не принимать новую конвертацию категории, показать время восстановления |
| Хранилище заполнено | Не запускать новую конвертацию, предложить удалить файлы/очистить хранилище |

Сетевой сбой и ошибка сервиса показываются отдельно от ошибки формата. Сохраняются выбранное направление и допустимые настройки; если браузер потерял файл, пользователь выбирает его снова. В ошибках не раскрываются внутренние пути, секреты и трассировки.

### 8.2. Пакет

Все файлы одной операции обрабатываются **в одном направлении**. PDF → DOCX и DOCX → PDF нельзя смешать в одном пакете.

Если осталось 2 попытки, а передано 5 допустимых документов, к обработке допускаются **первые два** в порядке пакета. Для остальных трёх объясняется отказ из-за остатка квоты. Это отличается от превышения максимального числа файлов тарифа: такой недопустимый запрос отклоняется по числу файлов.

Ошибка одного допущенного файла не останавливает остальные. Файл подсвечивается с причиной, попытка за его неуспех не списывается. Следующий из ранее отклонённых файлов **автоматически не подставляется**: пользователь отправляет его заново.

### 8.3. Закрытие вкладки и сеть

Перед закрытием вкладки во время обработки запрашивается подтверждение. После закрытия уже принятое сервером задание продолжается; результат подтверждённого аккаунта доступен в кабинете. Завершение страницы не является отменой задания.

Браузерный диалог имеет ограничения: текст задаётся браузером, показ зависит от взаимодействия со страницей, событие ненадёжно в отдельных сценариях, особенно на мобильных устройствах. Серверная обработка и сохранение не должны зависеть от показа предупреждения. Основание: [MDN — beforeunload](https://developer.mozilla.org/en-US/docs/Web/API/Window/beforeunload_event).

При сетевом сбое:

- без успешной серверной обработки попытка не списывается;
- автоматического повтора нет, пользователь заново добавляет файлы для новой конвертации;
- если сервер уже успешно сконвертировал и сохранил файл, но ответ потерян, **попытка списывается**, результат остаётся в кабинете;
- новая ручная конвертация — новая обработка с обычным списанием при успехе; повторное скачивание готового результата попытку не расходует.

**Отмена уже принятого задания не предусмотрена:** ни в интерфейсе, ни через API. Системная остановка при удалении аккаунта выполняется по разделу 6.4. При обрыве скачивания пользователь повторно нажимает кнопку или программа отправляет новый запрос на скачивание; архив скачивается с начала. Продолжение с места обрыва в первой версии не поддерживается. Готовые результаты повторно не конвертируются, попытки не расходуются; действуют исходный срок доступности и проверка доступа.

## 9. API сервиса

API принимает файл/файлы и направление конвертации, проверяет действительный ключ и применяет права владельца. Без действительного ключа конвертация не выполняется. Бесплатный базовый тариф имеет API-доступ; платная подписка не является условием самого доступа.

Платным тарифам через API доступно **до 5 файлов** в одном направлении, с теми же остатками квоты, частичным допуском и ошибками, что на сайте. Счётчики общие. Результаты обязательно сохраняются в кабинете владельца ключа.

### 9.1. Принятие задания и получение результата

**Асинхронная обработка:**

1. Клиент отправляет файлы и параметры конвертации.
2. После проверки запроса и допуска к обработке API возвращает `202 Accepted` и идентификатор задания. Это подтверждение принятия, а не успешной конвертации.
3. Клиент отдельными запросами проверяет состояние задания по идентификатору.
4. После завершения клиент получает сведения об успешных результатах и ошибках/отказах отдельных файлов; успешные результаты доступны для скачивания в ZIP по правилам раздела 10.2.

Клиенту не требуется держать исходное соединение открытым до завершения конвертации. Принятая обработка продолжается при отключении клиента. Получение состояния и повторное скачивание готового результата не являются новой конвертацией и не расходуют попытку. Правила списания при успехе и сетевом сбое определены в разделах 4 и 8.3. Автоматическая повторная отправка файлов не добавляется.

**Отмена принятого задания не предусмотрена**, включая отмену через API. Удаление аккаунта приводит к специальной системной остановке по разделу 6.4. Webhook отдельно не заявлен.

### 9.2. Клиенты и границы доступа

Клиенты первой версии — **наш сайт, боты и программы для тестирования**. Интеграция со сторонними сайтами, включая прямые обращения из их браузерных страниц, в объём первой версии не входит. Telegram-бот остаётся вторым этапом по разделу 13.

Боты и тестовые программы обращаются к публичному API с действительным пользовательским ключом. Собственный сайт сохраняет установленные сценарии гостя и авторизованного пользователя; использование сайта не требует от посетителя ручного создания или ввода API-ключа. Гостевой веб-сценарий не предоставляет доступ к публичному API без ключа.

### 9.3. Доступ к состоянию задания и ZIP

Каждый запрос к публичному API на проверку состояния задания или скачивание ZIP требует **действующего API-ключа аккаунта, которому принадлежат задание и результат**. Одного идентификатора задания или результата для доступа недостаточно. Запрос без действующего ключа либо с ключом другого аккаунта не предоставляет состояние задания и файлы.

После замены ключа новый действующий ключ того же аккаунта позволяет проверять его ранее созданные задания и скачивать сохранённые результаты в пределах их срока доступности. Старый или отключённый ключ доступа не даёт. При отключении ключа без выпуска нового API-доступ отсутствует; правила доступа через кабинет сохраняются.

Скачивание выдаёт ZIP с составом по разделу 10.2; истечение срока или удаление результата прекращает его выдачу. При прерывании скачивания клиент вручную запрашивает ZIP заново и получает архив с начала. Это не новое задание и не дополнительное списание попытки. Для собственного сайта действуют проверка пользовательской сессии либо гостевой доступ по разделу 10.1, без требования ручного ввода API-ключа.

### 9.4. Контракт и документация

Техническая спецификация API до реализации должна закрепить базовый адрес, версию/методы/пути, заголовок ключа, передачу файлов и параметров страниц/объединения/качества, частичный ответ пакета, ошибки, сроки и получение ZIP с соблюдением установленных правил доступа. Адреса, поля и заголовки определяются техническим контрактом API без изменения требований разделов 8–10.

Ключ передаётся в заголовке, не URL; сервер проверяет владельца каждого задания/результата. Ошибка содержит машинный код, понятное описание и идентификатор запроса без секретов. Категории HTTP для технического контракта: `2xx` успех/принятие, `400` запрос, `401` ключ, `403/404` доступ/объект, `413` размер, `415` тип, `422` содержимое, `429` ограничения, `5xx` ошибка сервиса. Точное соответствие утверждается с контрактом.

Документация API должна содержать примеры принятия задания, проверки состояния, успеха, ошибки, частичного результата и получения ZIP, включая отказ без действующего ключа или при обращении к чужому заданию. Частота проверки состояния ограничена разделом 3.8; примеры API должны соблюдать общий минутный предел и интервал одного задания. Дополнительная защита от массовых запросов задана в разделе 12.13.

### 9.5. Дополнения API для бота второго этапа

Для сценария раздела 13 на этапе 2 API дополняется следующими возможностями без назначения в этом ТЗ конкретных путей и полей:

- Проверка ключа и получение ID его владельца, актуального тарифа, пакетных/размерных ограничений, остатков и сроков блокировок, состояния хранилища. Пароли, почтовые коды и чужие данные не возвращаются.
- Подготовка исходника до запуска: после проверки типа, размера и антивируса — получение числа страниц PDF и защищённого идентификатора подготовленного файла для выбора страниц. Это не конвертация и не списание попытки; такой файл доступен только владельцу и текущему черновику, не сохраняется в профиль и истекает после 30 минут без активности. Подготовка соблюдает ограничения памяти/времени и общей занятости обработки, не создаёт неограниченный обход очереди. Запросы подготовки используют группу создания с пределом 10 в минуту; информационные запросы — общую группу состояния 120 в минуту по разделу 3.8.
- Принятие идентификатора клиентской операции и поиск её задания: повтор того же идентификатора у того же владельца возвращает прежнее задание, без новой загрузки/обработки и списания. Иное содержимое с тем же идентификатором отклоняется. Учёт и поиск операции сохраняются 30 дней; после истечения идентификатор не используется для автоматического нового запуска. Повторная осознанная конвертация создаётся с новым идентификатором. API проверяет владельца, даже если ключ заменён.

Потеря ответа не разрешает боту автоматически повторно отправлять исходники. Состояния успешной конвертации и доставки архива в Telegram различаются. Эти дополнения относятся к этапу 2; отсутствие их в приёмке первой версии не является дефектом.

## 10. Хранение и скачивание

### 10.1. Сохраняемые данные и сроки

В аккаунте сохраняются **все успешные сконвертированные результаты**, включая базовый тариф и API. Переключателя отключения сохранения нет. Исходники в профиль не сохраняются, используются только временно для обработки.

| Контекст | Срок от готовности результата |
| --- | --- |
| Подтверждённый аккаунт любого тарифа | 6 календарных месяцев |
| Гость или неподтверждённый аккаунт | Скачивание в течение 12 часов |

Повторное скачивание не продлевает срок. Пользователь может скачать результат в любой момент срока, если сам не удалил его раньше.

**Возвращение гостя к результатам:** после закрытия вкладки и повторного открытия сайта в том же браузере доступны его задания и результаты с неистёкшим сроком. Для каждого готового результата срок скачивания — 12 часов от готовности; повторное открытие сайта его не продлевает. Уже принятая обработка продолжается после закрытия вкладки. После очистки данных браузера либо с другого браузера или устройства восстановление гостевого доступа не предусмотрено; отдельная секретная ссылка не выдаётся. Эти правила применяются и к неподтверждённому аккаунту, пока он работает по гостевым правилам.

Идентификация гостя и последствия очистки cookie для квот определены в разделе 4.2. Учёт попыток неподтверждённого аккаунта во всех браузерах не предоставляет ему кабинет или восстановление доступа к гостевым результатам с другого устройства: до подтверждения правила выдачи результатов остаются гостевыми.

Показывается дата окончания доступности результата. После истечения срока выдача прекращается, учитываемый объём освобождается, файл физически удаляется по срокам раздела 10.4. Правила очистки временных исходников и рабочих данных также определены там. Состав, сроки и правила резервных копий заданы в разделе 10.5.

### 10.2. ZIP

- Для каждого исходного файла своя кнопка скачивает ZIP **только с его результатами**.
- PDF → изображения: внутри ZIP изображения выбранных страниц этого PDF.
- При выключенном объединении у каждого изображения своя кнопка ZIP с отдельным PDF.
- Для объединённых изображений одна кнопка скачивает ZIP **с одним итоговым PDF**.
- ZIP используется даже для единственного выходного файла.
- ZIP создаётся для скачивания, **постоянно не хранится и после скачивания удаляется**. Повторное скачивание создаёт новый временный ZIP, не новую конвертацию.
- При обрыве скачивания пользователь или программа вручную запрашивает архив заново. Он создаётся из уже готовых результатов и скачивается с начала; продолжения с места обрыва в первой версии нет. Попытки не списываются, срок доступности не продлевается.
- В квоту входит объём только готовых файлов, ZIP-копия повторно не учитывается.

Имена результатов позволяют сопоставить исходник/номер страницы; при ошибке или прерывании выдачи также очищается временный ZIP. Дополнительная общая кнопка ZIP всего пакета не входит в установленный объём первой версии.

### 10.3. Заполнение и удаление

| Тариф | Хранилище | Предупреждение при 75% |
| --- | --- | --- |
| Базовый | 5 ГБ | 3,75 ГБ |
| Pro | 15 ГБ | 11,25 ГБ |
| Максимальный | 50 ГБ | 37,5 ГБ |
| Enterprise | По договорённости | 75% установленного объёма |

При достижении 75% предупреждать, что место скоро закончится. При полном хранилище **новая конвертация недоступна**; предложить удалить отдельные файлы или очистить всё хранилище. Оба действия доступны. Старые файлы автоматически ради новых не удаляются.

Если место было при допуске, но результат оказался больше остатка, **последний результат сохраняется сверх квоты**, затем новые операции блокируются. Если первый результат допущенного пакета заполнил хранилище, остальные уже принятые файлы **продолжают обрабатываться и сохраняться сверх квоты**. Это не разрешает принимать новые операции при заполненном хранилище.

При понижении тарифа старые результаты сохраняются до конца своих сроков. Например, занято 20 ГБ, новая квота 15 ГБ: скачивание старых файлов доступно, новые конвертации запрещены до освобождения места.

Занятый объём определяется по готовым файлам без ZIP, исходников и рабочих файлов; обновляется при удалении/истечении срока. При 100% и выше сервер отклоняет новые операции сайта/API без списания попытки. Полная очистка требует явного подтверждения; удаление проверяет владельца. Ошибка сохранения не показывается как успешное сохранение; она отделяется от результата самой конвертации.

### 10.4. Очистка временных и готовых файлов

**Временные исходники и рабочие файлы** удаляются сразу после успеха, ошибки либо прекращения загрузки; предельный срок очистки — **15 минут после соответствующего события**. Исходники уже принятых заданий, ожидающих очереди, сохраняются до обработки и не удаляются только из-за длительности ожидания. После удаления аккаунта временные файлы его остановленных заданий также подлежат очистке.

После сбоя оставшиеся временные исходники и рабочие файлы очищаются **в течение часа после восстановления работы**. Это не продлевает доступность готовых гостевых или пользовательских результатов. Для временных ZIP сохраняется правило удаления после скачивания по разделу 10.2; ошибка или обрыв выдачи не являются основанием для постоянного хранения ZIP.

При удалении отдельного готового результата, полной очистке хранилища, удалении аккаунта или истечении срока хранения:

1. Доступ к соответствующим файлам и их выдача прекращаются **сразу**.
2. Учитываемый объём в кабинете освобождается **сразу**, без ожидания физической очистки.
3. Файлы физически удаляются из **основного хранилища в течение часа**.

Результат нельзя скачать или вернуть в список только потому, что физическая очистка ещё ожидается. Операция очистки хранилища сама по себе не отменяет уже принятые конвертации; специальная остановка всех заданий применяется при удалении аккаунта по разделу 6.4.

Сроки доступности не меняются: 12 часов от готовности для гостя и неподтверждённого аккаунта, 6 календарных месяцев для подтверждённого аккаунта. Резервные копии и их удаление регулируются разделом 10.5; срок физической очистки основного хранилища не является сроком очистки резервных копий.

### 10.5. Резервные копии и восстановление

В резервное копирование включаются **данные аккаунтов, тарифов/подписок, заданий и сохранённые результаты подтверждённых пользователей**, включая базовый тариф. Гостевые файлы, результаты неподтверждённых аккаунтов по гостевым правилам, исходники, рабочие файлы и временные ZIP в копии не включаются. Наличие сведений о задании в копии не означает резервирования его временного исходника или гостевого результата.

Копии хранятся **зашифрованными, отдельно от основного хранилища**, с ограниченным служебным доступом. Выбор технологии копирования, хранилища и управления ключами описывается в отдельном файле technology-stack.md; хранилище копий размещается в ЕС по разделу 12.2; шифрование и правила доступа/использования содержимого согласованы в разделах 12.5–12.7.

Резервная копия создаётся **не реже одного раза в сутки**. Точки восстановления хранятся **30 дней от создания**, после чего автоматически удаляются. При восстановлении из последней успешной ежедневной копии могут быть потеряны изменения после её создания — при штатном выполнении копирования до 24 часов. Контроль ошибок копирования и порядок восстановления после аварии согласованы в разделах 12.10–12.11.

Удалённые файлы и аккаунты могут оставаться только в ранее созданных копиях **до окончания их 30-дневного срока хранения**. Пользовательского доступа к этим данным нет; восстановление удалённых пользователем данных как пользовательская функция не предоставляется. Новые копии не должны заново включать уже удалённые аккаунты/результаты и тем самым продлевать срок сохранения их данных.

**До возобновления доступа к восстановленному сервису** повторно применяются актуальные сведения об удалениях аккаунтов/файлов и сроках хранения. Удалённые аккаунты, удалённые файлы и просроченные результаты не должны снова становиться доступны, попадать в список пользователя или занимать учитываемый объём хранилища. Восстановление не запускает заново срок 12 часов или 6 месяцев: используется исходная дата готовности результата.

Сведения, необходимые для повторного применения удалений, должны сохраняться независимо от отката к выбранной старой точке восстановления и быть доступны, пока существуют содержащие эти данные копии. Восстановление не должно отменять подтверждённое удаление аккаунта или создавать доступ к его прежним заданиям и результатам. Конкретный механизм фиксируется в технической реализации с соблюдением этих правил.

Срок удаления копий не заменяет сроки раздела 10.4: доступ к удаляемым готовым файлам и учёт объёма прекращаются сразу, физическая очистка основного хранилища выполняется в течение часа. Копии предназначены для аварийного восстановления сервиса и не продлевают пользовательский срок хранения файлов.

## 11. Подписка, отмена и возвраты

### 11.1. Активация и продление

Оплата картой, месяц или год. **Автопродление выключено по умолчанию**, пользователь может включить его сам.

Выключение только автопродления сохраняет оплаченные возможности до конца срока, следующего автоматического списания нет. По окончании срока применяется базовый тариф.

Если к концу оплаченного периода при **включённом автопродлении** оплата следующего периода не подтверждена, даются **24 часа от окончания оплаченного периода** с сохранением всех возможностей прежнего платного тарифа. Ошибки и повторные попытки не продлевают этот срок. Без успешной оплаты до его окончания пользователь переводится на базовый тариф. Если автопродление выключено к концу оплаченного периода, применяется базовый тариф без льготных суток. Подробности повторов и дат — в разделе 11.8.

Права активируются после серверной проверки оплаты; сумма, валюта, тариф и аккаунт сверяются. Повторное подтверждение платежа не продлевает период дважды. Автоматические повторы неуспешного продления выполняются по разделу 11.8.

### 11.2. Немедленная отмена

Отмена подписки прекращает платные возможности **с момента отмены**, применяется базовый тариф и прекращаются дальнейшие списания. На карту возвращается часть оплаты за **неиспользованный остаток периода**, не на внутренний баланс.

Пример: отмена ровно в середине месячного периода — половина оплаты: Pro €2,50, максимальный €5.

Действия «Выключить автопродление» и «Отменить подписку» должны быть различимы: первое сохраняет оплаченный доступ до конца срока, второе прекращает его сразу с частичным возвратом.

### 11.3. Повышение, понижение, удаление аккаунта

- Pro → максимальный применяется сразу с доплатой за неиспользованный остаток текущего периода.
- Немедленное понижение доступно; разница за неиспользованный срок возвращается **на карту**, не баланс.
- При удалении аккаунта активная подписка прекращается и будущие списания останавливаются **без создания возврата за остаток оплаченного периода**, по разделу 6.4. Это не самостоятельная отмена подписки с возвратом по разделу 11.2.

При переходе **Pro ↔ максимальный с сохранением типа оплаты** (месяц остаётся месяцем либо год остаётся годом) **дата окончания оплаченного периода сохраняется**. Доплата или возврат относятся только к оставшемуся времени. Например, если месячная подписка заканчивалась 20 ноября, после повышения она также заканчивается 20 ноября.

Для простого случая без предыдущих перерасчётов разница за остаток одного и того же периода равна разнице соответствующих полных тарифных цен, умноженной на долю оставшегося времени в этом периоде. Пример: максимальный €10/месяц → Pro €5/месяц ровно в середине — возврат €2,50. Для годовой оплаты используются €51/€102 со скидкой. При нескольких сменах действует полный учёт истории по разделу 11.7, а не повторное применение упрощённой формулы к последнему платежу.

Календарь, точность и округление определены в разделах 11.4–11.5; смена месяца/года и учёт предыдущих операций — в разделах 11.6–11.7. Состояния возврата отделяются от отмены: ожидание/успех/ошибка; срок банковского возврата не назначен до выбора платёжного сервиса. Повторная обработка удаления/возврата не должна возвращать деньги дважды.

### 11.4. Календарные периоды подписки

Первый платный период начинается **в момент активации после успешной оплаты**, подтверждённой сервером по разделу 11.1. Месячная подписка действует **календарный месяц**, годовая — **календарный год**, с сохранением времени начала. Расчётное время и границы периодов задаются в **UTC**. При своевременной оплате продления в льготные сутки график сохраняется по разделу 11.8.

Если исходного числа в очередном месяце нет, используется его последний день. В последующих периодах сохраняется исходное число, а не число короткого месяца: например, **31 января → последний день февраля → 31 марта**. Для годовых периодов также учитываются календарь и високосные годы; при отсутствии исходной даты используется последний день соответствующего месяца.

Конец нового календарного периода вычисляется по этим правилам. Смена тарифа при сохранённом типе оплаты оставляет прежний конец периода по разделу 11.3; переход месяц ↔ год начинает новый период по разделу 11.6.

### 11.5. Точность перерасчёта и округление

Использованное и оставшееся время рассчитываются **с точностью до секунды**, по фактической длительности соответствующего оплаченного периода. Не используется условная длительность 30 дней для каждого месяца или одинаковое число дней для любого года.

При годовой подписке расчёт основан на цене со скидкой: **€51 для Pro и €102 для максимального тарифа**, а не на месячной цене, умноженной на 12. Предыдущие смены тарифа, доплаты и выполненные возвраты учитываются по разделу 11.7; вся история не пересчитывается только по последнему платежу.

**Округляется только итоговая сумма операции доплаты или возврата до одного евроцента.** Промежуточные значения не округляются. Меньше половины цента округляется вниз, половина цента и больше — вверх: **€2,345 → €2,35**, **€2,344 → €2,34**. Расчёт должен сохранять это правило без ошибок представления денежных дробей; конкретные средства реализации выбираются в файле технологий.

### 11.6. Переход месяц ↔ год

При изменении типа оплаты **месяц ↔ год начинается новый полный календарный период с момента успешного перехода**. Правило действует и при одновременной смене тарифа. Новый конец периода рассчитывается по разделу 11.4 от этого момента.

Стоимость неиспользованного остатка старой подписки **однократно засчитывается в оплату нового периода**. Если её недостаточно, пользователь доплачивает разницу. Если она превышает стоимость нового полного периода, разница возвращается на карту. Перерасчёт учитывает годовую скидку, секунды, итоговое округление и историю операций по разделам 11.5 и 11.7.

Это учёт стоимости в рамках конкретного перехода; пользовательский внутренний денежный баланс не создаётся. Уже использованное время старой подписки не засчитывается повторно и не возвращается.

### 11.7. История оплат, доплат и возвратов

При каждой смене тарифа, периода оплаты и последующей отмене учитывается **вся история оплат, доплат, использованного времени и уже выполненных возвратов**. Один и тот же неиспользованный остаток может быть зачтён или возвращён только один раз.

Возврат ограничен **фактически оплаченными и ещё не возвращёнными средствами, относящимися к неиспользованному времени**. Суммы, уже отнесённые к другой операции возврата или зачёта, не используются повторно, включая конкурентные и ещё ожидающие завершения операции. Техническая реализация связывает расчёт с исходными платежами и историей операций, чтобы не выдавать повторный возврат из-за повторного запроса или уведомления.

**Контрольный пример:** Pro за €5 → ровно в середине периода повышение до максимального с доплатой €2,50 → немедленная отмена. Возврат составляет **€5**: €2,50 оставшегося Pro и €2,50 доплаты. Уже использованная половина Pro возврату не подлежит. Пример предполагает совпадающий момент повышения/отмены для проверки расчёта, без дополнительного использованного времени между операциями.

Отдельного продуктового ограничения числа смен тарифа в первой версии нет. Денежные операции не выполняются конкурентно для одной подписки и проходят установленные проверки оплаты/возврата. Правила счётчиков, таймеров и текущих заданий при переходах определены в разделах 4.1 и 4.3; смена типа оплаты без смены уровня тарифа квоту не обновляет.

### 11.8. Льготные сутки и повторная оплата продления

Льготный срок начинается **в момент окончания оплаченного периода** при включённом автопродлении и отсутствии подтверждённой оплаты следующего периода. Он длится **24 часа**, сохраняет все возможности прежнего тарифа и не перезапускается из-за ошибок либо повторных запросов. Пользователю показываются состояние ожидания оплаты и время окончания льготного срока.

После неуспешной плановой оплаты предусмотрены **два автоматических повтора**:

| Повтор | Время от начала льготных суток |
| --- | --- |
| Первый | Через 1 час |
| Второй | Через 12 часов |

Пользователь также может повторить оплату вручную. Автоповторы выполняются только для случаев, допускаемых платёжным сервисом. Если нужно подтверждение банком, исправление платёжных данных или замена карты, сервис предлагает соответствующее действие пользователю вместо неподходящего автоматического списания. Конкретные статусы и ограничения провайдера учитываются при его интеграции в файле технологий.

Успешная оплата прекращает дальнейшие повторы этого продления. Одновременные автоматические и ручные попытки не должны создавать двойное списание либо несколько независимых продлений; при уже выполняющейся оплате нельзя запускать конкурирующее списание той же суммы за тот же период.

При успешной оплате **в течение льготных суток** следующий период считается **от прежней даты окончания подписки**, а не от момента поздней оплаты; исходный календарный график продлений сохраняется. Если 24 часа истекли без успешной оплаты, применяется базовый тариф. **Новая покупка после этого** начинает новый полный период от активации по разделу 11.4.

Если автопродление было выключено к окончанию оплаченного периода, льготные сутки не предоставляются и автоматические списания не выполняются. Неуспешная доплата и запоздавшие подтверждения/списания регулируются разделами 11.9 и 11.11. Выключение автопродления, отмена и смена подписки внутри льготных суток определены в разделе 11.12.

### 11.9. Неуспешная доплата при смене подписки

Если для смены тарифа или типа оплаты требуется доплата, **до её подтверждения сохраняются прежний тариф и даты периода**. При ошибке показываются понятная причина и возможность повторить оплату; новые оплачиваемые возможности не включаются. Неподтверждённая доплата не выполняет окончательный переход и не запускает новый период.

Повторные запросы и уведомления не создают дополнительные списания или несколько применений одного перехода. Ранее оплаченные права сохраняются до их исходного окончания, если пользователь отдельно не отменил подписку. Действия внутри уже неоплаченного льготного срока выполняются по разделу 11.12.

### 11.10. Ошибки возврата и повторные попытки

**Ошибка возврата не отменяет уже выполненную отмену или понижение тарифа.** Рассчитанная сумма сохраняется к возврату; обязательство не считается исполненным только из-за ошибки запроса. Пользователю показывается актуальное состояние возврата: ожидание, обработка/выполнение по подтверждённым данным провайдера либо ошибка.

Для **подтверждённой временной технической ошибки**, допускающей повтор, выполняются до трёх автоматических повторов от момента первой ошибки:

| Повтор | Время от первой ошибки возврата |
| --- | --- |
| Первый | Через 1 час |
| Второй | Через 6 часов |
| Третий | Через 24 часа |

Перед повтором проверяется состояние предыдущего запроса у провайдера. Ожидание обработки провайдером/банком не является основанием отправлять ещё один возврат. Неизвестный результат сетевого запроса сначала выясняется, а не приравнивается к подтверждённой неудаче. Подтверждённый выполненный возврат повторно не отправляется.

После исчерпания автоматических повторов неразрешённая ошибка направляется администратору. Постоянный отказ, не допускающий повтора, передаётся на разбор без неподходящих автоматических попыток. **Администратор может повторить ту же операцию без изменения рассчитанной суммы**; поддержке это изменяющее право не предоставляется. Это не произвольный новый возврат и не возможность редактировать сумму через панель.

Автоматические и ручные повторы относятся к одной операции, проверяются на сервере и не приводят к двойному возврату. История и зарезервированные под возврат суммы учитываются по разделу 11.7; действия администратора журналируются по разделу 12.14.

Подтверждение обработки возврата провайдером не определяет момент поступления денег на карту. Статус обновляется по актуальным подтверждённым сведениям; банковский срок не задаётся до выбора платёжного сервиса. Получение новой ошибки после предварительного подтверждения должно отражаться в состоянии операции.

### 11.11. Запоздавшие платёжные подтверждения и списания

При задержке уведомления сервис проверяет **фактическое время успешной оплаты у провайдера**, а не считает временем оплаты только получение уведомления. Если оплата выполнена в льготные сутки и операция остаётся актуальной, задержка уведомления сама по себе не делает оплату просроченной; применяется исходный график по разделу 11.8.

Если подтверждено списание **после истечения срока неоплаченного продления**, либо оно относится к **отменённой операции, удалённому аккаунту или подписке, которую пользователь уже заменил другой покупкой**, прежняя подписка не возобновляется. Устаревшее списание **полностью возвращается на карту** по правилам контроля и повторов раздела 11.10. Возврат не создаёт пользовательский баланс и не восстанавливает удалённый аккаунт.

**Уже учтённый платёж повторно не обрабатывается.** Запоздавшее или повторное уведомление не является основанием ещё раз активировать подписку, продлить период либо вернуть деньги, если соответствующая операция уже учтена. Применение своевременно оплаченного продления не должно заменять более позднюю актуальную покупку пользователя.

### 11.12. Действия внутри льготных суток

Если льготные сутки уже идут, **выключение автопродления или отмена подписки сразу прекращают повторные оплаты и переводят пользователя на базовый тариф**. За неоплаченный период возврат не начисляется; дополнительный долг за предоставленные льготные часы не создаётся. Уже учтённые оплаченные операции и их возвраты при этом не дублируются.

Для смены тарифа или типа оплаты при неоплаченном продлении доступны **два последовательных варианта**:

1. Оплатить текущее продление, затем выполнить обычную смену подписки с учётом оплаченного остатка.
2. Отменить неоплаченное продление и оформить новую покупку полного периода. После отмены старого продления до успешной новой покупки действует базовый тариф.

Неоплаченные льготные часы **не создают денежного остатка для зачёта**. Новая покупка после отмены продления начинает новый полный календарный период от активации. Своевременно оплаченное текущее продление сохраняет исходный график по разделу 11.8. Запоздавшие списания за уже отменённое или заменённое продление обрабатываются по разделу 11.11.

### 11.13. Уведомления о возврате после удаления аккаунта

**Удаление аккаунта само по себе не запускает возврат за неиспользованный срок подписки.** Правила этого раздела применяются только к ранее возникшему возврату либо возврату ошибочного/устаревшего списания по разделу 11.11. Удаление не создаёт новую операцию возврата за уже оплаченный остаток и не дублирует ранее учтённые операции.

Если такая операция возврата существует после удаления аккаунта, уведомления о её состоянии отправляются **на его последний подтверждённый email**. Аккаунт и доступ к кабинету не восстанавливаются; письмо относится к конкретной операции возврата, а не предоставляет новый вход в сервис.

Контактный email для этой операции хранится **отдельно до успешного завершения возврата** и удаляется **в течение 30 дней после успешного завершения**. Он используется только для уведомлений и разбора возврата. Ошибка или ожидание обработки не приравниваются к успешному завершению и не прекращают необходимую связь по незавершённой операции.

Эта ограниченная служебная контактная запись не является сохранённым пользовательским аккаунтом и не разрешает удерживать удалённые файлы. Действуют установленные шифрование и ограничения доступа. Продавец — ФОП в Украине; состав и порядок хранения остальных финансовых сведений указаны в разделе 11.15.

Если операции возврата нет, отдельная контактная запись для её сопровождения только из-за удаления аккаунта не создаётся.

### 11.14. Enterprise и минимальные денежные операции

В первой версии Enterprise представлен **договорной ценой и кнопкой обращения в поддержку по email**, без автоматической покупки или ручной активации особого тарифа администратором. Реализация индивидуальных договорных условий вынесена в отдельный будущий объём по разделу 15.1. До него используются только фиксированные тарифы; отображение Enterprise не назначает неограниченную квоту, произвольную цену или дополнительные права автоматически.

**Сервис не устанавливает собственного минимального порога доплат и возвратов.** Положительная рассчитанная сумма учитывается с точностью до **€0,01** по установленному правилу округления. Минимум конкретного платёжного сервиса фиксируется при его выборе как техническое ограничение, а не как право увеличить сумму, изменить формулу или списать обязательство.

- Если положительная доплата допустима провайдером, списывается именно рассчитанная сумма. Если она ниже технического минимума, переход не выполняется: прежние тариф и период сохраняются, пользователь видит причину и может повторить действие позже. Доплата не увеличивается до минимума, повышение не предоставляется бесплатно, внутренний баланс не создаётся.
- Если положительный возврат допустим провайдером, возвращается именно рассчитанная сумма на карту. Если выполнить такой возврат технически нельзя, сумма **остаётся обязательством сервиса**, операция получает понятный статус «Требуется урегулирование поддержкой» и передаётся на разбор. Сумма не сгорает, не превращается автоматически в бонус или внутренний баланс; отмена/понижение тарифа не откатываются.
- Разбор поддержки не означает успешного возврата. До подтверждённого фактического исполнения сохраняются точная сумма, связь с исходным платежом и статус обязательства; действуют защита от повторов и сопровождение после удаления аккаунта по разделам 11.7, 11.10 и 11.13. Способ возврата на карту не заменяется автоматически иным способом.
- Если после установленного округления итог равен **€0,00**, денежная операция не создаётся; это не технический отказ положительной суммы. Изменение тарифа может применяться без списания при соблюдении остальных условий операции. Ошибочный или неопределённый ответ провайдера нельзя считать нулевой суммой.

Технические пределы провайдера описываются в файле технологий. Подробный регламент ручного урегулирования малых возвратов находится за пределами настоящего ТЗ. До фактического исполнения обязательство сохраняется; неисполненный возврат нельзя отмечать успешным.

Продавец — **ФОП в Украине**. Серверная обработка и хранение размещаются **в ЕС** по разделу 12.2. Финансовые сведения хранятся по разделу 11.15.

### 11.15. Финансовые сведения ФОП

**Продавец — ФОП в Украине.**

Сохраняется минимальный реестр оплат и возвратов: идентификаторы операций, сумма и валюта, даты, тариф и оплаченный период, статус, ссылки/идентификаторы подтверждений платёжного провайдера и минимальный служебный идентификатор клиента для сопоставления операций. Полные карточные реквизиты, пароли и содержимое конвертируемых файлов в этот реестр не включаются.

Необходимые финансовые сведения хранятся отдельно от пользовательского профиля. Удаление аккаунта не удаляет финансовую запись раньше применимого обязательного срока и не сохраняет либо восстанавливает файлы пользователя. Отдельный email для незавершённого возврата по-прежнему регулируется разделом 11.13.

Правовая основа для определения сроков — [п. 44.3 Налогового кодекса Украины в публикации ДПС](https://tax.gov.ua/nk/spisok2/glava-1--zagalni-polojennya-/). Для категории подп. 44.3.3 указан минимум 1095 дней; для других категорий предусмотрены более длительные сроки. Начало отсчёта и продления определяются применимыми положениями, поэтому универсальный срок «3 года от платежа» всем финансовым сведениям не назначается.

Для финансовых сведений определяются категория, соответствующая дата начала отсчёта и применимые основания продления; автоматическая очистка не выполняется до окончания обязательного хранения. Конкретная настройка учитывается при интеграции оплаты и организации учёта ФОП. Это требование относится к финансовым сведениям об услуге и не продлевает хранение загруженных документов, готовых результатов или обычных технических журналов.

## 12. Безопасность и эксплуатация

### 12.1. Базовые технические механизмы

Следующие требования безопасности обязательны для реализации и приёмки:

- HTTPS для сайта, API и скачивания; проверка сессии, подтверждения email и владельца профиля, задания, файла, ключа при каждом защищённом действии.
- Защищённое хранение паролей без открытого/обратимо зашифрованного вида; защита сессий и изменяющих аккаунт запросов от подделки, безопасный вывод имён/данных.
- Почтовые и резервные коды восстановления, пароли, API-ключи, содержимое документов и секретные ссылки не попадают в журналы/ошибки. Подтверждения кодами и тарифные запреты проверяются сервером.
- Изоляция процессов конвертации; отсутствие исполнения содержимого файла и неконтролируемого доступа к сети/файловой системе из документа.
- Контроль распаковки DOCX, памяти, времени, пикселей, результата и параллельности. Превышение — контролируемая ошибка и очистка временных данных; установленные пиксельные ограничения и объём пакета указаны в разделе 3.4, распаковка DOCX/время/результат — в разделе 3.6. Память, параллельность и частота запросов согласованы в разделах 3.7–3.8. Отдельного продуктового лимита страниц нет по разделу 3.5.
- Проверка подлинности платёжных подтверждений, недопущение подмены цены/аккаунта и двойного списания/возврата. Полные карточные реквизиты не включаются в журналы сервиса.
- Журналы содержат только необходимые технические данные по разделу 12.14: технические события хранятся 30 дней, безопасность и доступ сотрудников — 90 дней; содержимое файлов, исходные имена и секреты не записываются.
- Проверка доступности конвертера/хранилища, ошибок очистки, исчерпания ресурсов и конкурентных операций без обхода квот.

### 12.2. Регион обработки и хранения

Серверная обработка файлов, база данных, временные файлы, основное хранилище и резервные копии размещаются **в Евросоюзе**. Это требование относится к инфраструктуре нашего сервиса. Конкретные страну, провайдеров и конфигурацию выбирают в отдельном файле technology-stack.md с соблюдением установленного региона.

### 12.3. Конвертация и внешние обработчики

Конвертация и OCR выполняются **в нашем серверном окружении** у выбранного хостинг-провайдера. Содержимое документов не отправляется сторонним API конвертации, OCR или ИИ. Выбор хостинга сам по себе не означает разрешение передавать документы дополнительным внешним сервисам обработки.

Почтовый и платёжный провайдеры выбираются отдельно в файле технологий; содержимое документов им не передаётся. Передача файлов через Telegram разрешена только для второго этапа по разделу 13 с предварительным уведомлением пользователя об этом канале. Конвертация, OCR и проверка файлов по-прежнему выполняются в нашем окружении; Telegram используется для передачи сообщений и файлов, а не как внешний конвертер.

### 12.4. Антивирусная проверка

**Каждый загруженный файл** на сайте и через API проверяется средствами антивируса в нашем серверном окружении **до создания миниатюр, конвертации и OCR**. Конкретное антивирусное средство и его настройка выбираются в файле технологий; отправка содержимого файлов внешнему сервису сканирования не допускается.

Если обнаружена угроза или проверку выполнить невозможно, включая недоступность средства проверки или отсутствие завершённого результата проверки, соответствующий файл отклоняется с понятной причиной **без списания попытки**. Обход проверки для продолжения конвертации не предоставляется. Остальные допустимые файлы пакета продолжают обрабатываться по общим правилам; автоматической замены отклонённого файла другим нет. Его временные данные удаляются по разделу 10.4.

### 12.5. Шифрование данных

Содержимое файлов и база данных **шифруются при хранении**. Требование распространяется на основное хранилище, временные исходники, рабочие файлы и временные ZIP; резервные копии шифруются по разделу 10.5. Передача данных сайта, API и скачивание выполняются по **HTTPS**.

**Ключи шифрования хранятся отдельно от защищаемых данных.** Для проверки и конвертации сервис получает доступ к расшифрованному содержимому в рамках разрешённых операций. Механизм хранения ключей должен обеспечивать восстановление и расшифровку установленных резервных копий в пределах их срока хранения.

Пароли защищаются без хранения в открытом или обратимо зашифрованном виде по разделу 12.1. Конкретные средства шифрования, защиты паролей и управления ключами выбираются в отдельном файле technology-stack.md.

### 12.6. Доступ сотрудников к содержимому

**Обычный просмотр пользовательских документов сотрудниками запрещён.** Обычная диагностика выполняется по техническим данным без просмотра содержимого файлов.

Для разбора обращения доступ сотрудника к содержимому **конкретных файлов** предоставляется только с **отдельного разрешения пользователя**, ограничивается этим обращением и фиксируется в журнале. Фиксируются сотрудник, время, основание и идентификаторы обращения/файлов; содержимое документа и секреты в журнал не включаются. По окончании разбора предоставленный доступ прекращается. Журнал доступа хранится 90 дней по разделу 12.14; роли поддержки и администратора заданы в разделе 12.15. Процедура запроса, подтверждения и отзыва разрешённого доступа к конкретным файлам задана в разделе 12.17.

Разрешение на разбор одного обращения не даёт общего доступа ко всем файлам пользователя и не разрешает использовать их для других целей. Автоматическая антивирусная проверка, конвертация, OCR, хранение и выдача выполняются служебными процессами в рамках установленных функций.

### 12.7. Допустимое использование содержимого

Содержимое пользовательских файлов используется **только для проверки безопасности, конвертации/OCR, хранения, резервного копирования, выдачи пользователю и отдельно разрешённого разбора его обращения**.

Пользовательские документы **не используются для обучения моделей, рекламы или тестирования продукта**. Для тестирования разработчик готовит отдельные контрольные документы либо использует материалы, отдельно предоставленные пользователем для этой цели. Файлы из обычных пользовательских конвертаций не копируются автоматически в тестовые наборы и среды разработки.

Правила использования содержимого распространяются на сайт и API. Сроки хранения и очистки определяются разделом 10.

### 12.8. Стартовая нагрузка и время ответа

Первая версия рассчитывается на **100 одновременно активных пользователей**, **не более 5 одновременно обрабатываемых задач конвертации на весь сервис** и **до 100 дополнительных задач в общей очереди**. Единица задачи определяется разделом 3.7: обычный исходный файл либо создание одного объединённого PDF. Индивидуальные пределы пользователя и общие пределы сервиса действуют одновременно.

Приём нового задания учитывает места как в пользовательской, так и в общей обработке/очереди. Если допустимые после проверки квот задачи нового запроса не помещаются, запрос отклоняется по правилам раздела 3.7 с понятной причиной **без списания попыток**. Заполнение общей очереди не отменяет ранее принятые задания.

При указанной нагрузке **не менее 95% обычных запросов кабинета, списка файлов и состояния заданий должны выполняться не дольше 2 секунд**. Проверяется серверное время выполнения запроса; пользовательская загрузка/скачивание файлов, антивирусная проверка и сама конвертация в этот показатель не включаются. Предел активной обработки файла остаётся 10 минут по разделу 3.6.

Разработчик готовит сценарии нагрузочной проверки с указанным числом активных пользователей, фоновой конвертацией и очередью. Результаты проверки должны подтверждать вместимость, соблюдение индивидуальных/общих ограничений и долю быстрых обычных запросов. Конкретная инфраструктура и технологии выбираются в отдельном файле technology-stack.md для выполнения установленных требований.

### 12.9. Доступность

Цель доступности сервиса — **не ниже 99,5% за календарный месяц**, включая плановые технические работы. Для 30-дневного месяца допустимая суммарная недоступность составляет **3 часа 36 минут**; для месяца другой длины рассчитывается 0,5% его продолжительности.

Показатель доступности относится к работе сервиса; предел активной конвертации 10 минут и время обычного запроса 2 секунды учитываются отдельно по разделам 3.6 и 12.8. Порядок мониторинга, обнаружения сбоев и аварийного восстановления задан в разделах 12.10–12.11.

### 12.10. Аварийное восстановление и задания

Основные функции сервиса восстанавливаются **в течение 2 часов после обнаружения аварии**. Восстановление включает работоспособность сайта/кабинета и API, приём и обработку допустимых заданий и выдачу доступных сохранившихся результатов. При необходимости используется последняя успешная резервная копия по разделу 10.5; допустимая потеря изменений после её создания при штатном ежедневном копировании остаётся до 24 часов.

После сбоя состояния заданий приводятся к следующему поведению:

| Состояние | Действие после восстановления |
| --- | --- |
| Задание ожидало обработки, исходники сохранились | Продолжает ожидать в очереди и затем обрабатывается в рамках общих и индивидуальных ограничений |
| Активная конвертация была прервана | Завершается понятной ошибкой без списания попытки; повторная отправка выполняется пользователем вручную |
| Задание успешно завершено, готовые результаты сохранились | Остаётся готовым, доступно по исходным правам/срокам; повторное списание попытки не выполняется |
| Задание ожидало обработки, исходник утрачен | Завершается понятной ошибкой без списания попытки; для новой конвертации пользователь вручную добавляет файл заново |

Продолжение ещё не начавшегося задания с сохранёнными исходниками не является повторным запуском прерванной конвертации. Состояние очереди, резервирование квот и списание успешных попыток согласуются так, чтобы не создавать повторную обработку или двойное списание. Восстановление не отменяет удаления аккаунтов/файлов и не продлевает сроки хранения по разделу 10.5.

### 12.11. Мониторинг и проверка резервных копий

Доступность сайта, API, хранилища и готовность обработки проверяются **раз в минуту**. При критическом сбое ответственный получает уведомление **не позднее чем через 5 минут после возникновения сбоя**. Конкретные средства мониторинга, канал уведомлений и назначение ответственного фиксируются при подготовке эксплуатации; технологии описываются в отдельном файле technology-stack.md.

Мониторинг отражает работоспособность основных функций, а не только наличие ответа от веб-сервера. По наблюдениям учитываются периоды недоступности, в том числе плановых работ, для месячного показателя раздела 12.9. Корректный отказ по тарифной квоте, установленному пределу запросов/очереди либо некорректному файлу сам по себе не считается аварией сервиса.

Контролируются успешность ежедневного копирования, ошибки копирования и **отсутствие успешной копии за последние 24 часа**. Ошибка либо отсутствие актуальной копии формируют критический сигнал ответственному с тем же предельным сроком уведомления 5 минут от обнаружения контрольной проверкой.

**Не реже одного раза в месяц** проводится тестовое аварийное восстановление в изолированном защищённом окружении. Проверяются возможность восстановления копии и расшифровки данных, основные функции, правила состояний заданий и отсутствие повторного доступа к удалённым аккаунтам/файлам и просроченным результатам.

Окружение проверки соблюдает установленные регион ЕС, шифрование, ограничение доступа и очистку данных. Проверка резервного восстановления является служебной операцией резервирования/восстановления и не разрешает обычный просмотр содержимого сотрудниками либо использование пользовательских документов для обучения, рекламы или тестирования функций продукта. Результат проверки фиксируется без содержимого и секретов.

### 12.12. Ограничения входа и почтовых сообщений

После **5 неверных паролей за 15 минут для аккаунта** вход по паролю приостанавливается **на 15 минут**. Счётчик относится к аккаунту, а не предоставляет отдельный предел с каждого нового IP. Действующие сессии не завершаются; восстановление пароля остаётся доступным с собственными ограничениями отправки/проверки кодов. Отказы во время действующей блокировки не являются новыми проверками пароля и не продлевают её срок.

На один email отправляется **не более 5 писем с кодами или инструкциями входа в час и 20 в сутки**. Предел общий для соответствующих операций регистрации, повторной регистрации занятого email, восстановления и изменений аккаунта. Для смены email учитывается адрес получателя каждого из двух последовательных писем. Дополнительно действуют правила раздела 6.1: повторный код не чаще одного раза в минуту, срок кода 10 минут и максимум 5 попыток его ввода. Этот предел не распространяется на платёжные уведомления.

При достижении ограничения сообщается время ожидания без раскрытия содержимого кода, пароля или факта наличия чужого аккаунта. Ограничения проверяются сервером. Они не меняют гостевые/тарифные попытки конвертации и не блокируют восстановление пароля только из-за приостановленного входа по паролю.

### 12.13. Дополнительная защита по IP

Для одного IP действуют следующие общие технические пределы:

| Действие | Предел |
| --- | --- |
| Динамические запросы сайта/API без статических ресурсов | 3 000 в минуту |
| Создание заданий | 60 запросов в минуту |
| Запросы отправки кодов и инструкций входа | 100 в час |
| Неверные попытки входа | 60 за 15 минут |

Пределы отдельных действий действуют одновременно с общим пределом динамических запросов и индивидуальными ограничениями аккаунта/гостя из раздела 3.8. При превышении соответствующие запросы отклоняются с объяснением времени ожидания. После превышения порога неверных входов вход с этого IP приостанавливается **на 15 минут**; это ограничение входа, а не запрет просмотра сайта или самостоятельная отмена принятых заданий.

Пользователи одной сети разделяют указанные технические пределы по IP, но **сохраняют отдельные квоты успешных конвертаций**. Общей продуктовой квоты 5 документов/5 изображений на IP нет. Изменение IP не сбрасывает счётчики аккаунта, а сохранённый гостевой cookie сохраняет свои счётчики по разделу 4.2. IP не используется как самостоятельное разрешение на доступ к чужим файлам.

### 12.14. Журналы и сроки хранения

| Вид журнала | Срок хранения от события |
| --- | --- |
| Технические журналы работы сервиса | 30 дней |
| События безопасности | 90 дней |
| Доступ сотрудников к файлам и основания такого доступа | 90 дней |

После соответствующего срока записи **автоматически удаляются**. Записываются время, действие, результат, длительность, IP и необходимые идентификаторы запроса, аккаунта, задания либо файла. Для служебного доступа также фиксируются сотрудник и основание/обращение по разделу 12.6.

**Содержимое документов, имена файлов, пароли, почтовые коды, API-ключи, ключи шифрования, секретные ссылки и другие секреты в журналы не включаются.** Требование применяется также к сообщениям ошибок и диагностике вспомогательных процессов. Идентификаторы используются для сопоставления событий без записи исходных имён и содержимого.

Журналы защищены от неразрешённого доступа и хранятся с соблюдением установленных региона и шифрования. Архивирование, копирование или восстановление не начинают срок хранения заново и не дают основания сохранять записи дольше 30/90 дней от исходного события; механизм очистки учитывает также копии и выгрузки журналов. Журналы доступны администратору по разделу 12.15; служебные права за пределами назначенной роли не предоставляются.

### 12.15. Служебные роли и вход сотрудников

Предусмотрены **две служебные роли**:

| Роль | Права |
| --- | --- |
| Поддержка | Просмотр необходимых данных пользователя, его лимитов, состояний заданий и оплат для разбора обращений |
| Администратор | Права поддержки; дополнительно просмотр служебных журналов и состояния системы, управление служебными учётными записями сотрудников, приостановка/возобновление новых конвертаций аккаунта и отдельное отключение его API-ключа по разделу 12.16; повтор неуспешного возврата без изменения суммы по разделу 11.10 |

Для обеих ролей обязательны **email, пароль и одноразовый код из приложения-аутентификатора**. Без успешного прохождения второго фактора доступ к служебным разделам и действиям не предоставляется. Подбор средств аутентификации выполняется в отдельном файле technology-stack.md; параметры почтовых кодов из раздела 6.1 не назначаются кодам приложения-аутентификатора.

Обычный пользователь не получает служебную роль через публичную регистрацию. Служебные права проверяются сервером при каждом защищённом запросе; скрытие элементов интерфейса не заменяет проверки полномочий.

Ни одна служебная роль не предоставляет обычного просмотра содержимого документов или раскрытия паролей, почтовых кодов и пользовательских API-ключей. Доступ к конкретным документам для обращения возможен только по отдельному разрешению пользователя и в рамках раздела 12.6; служебные действия и доступ фиксируются по разделу 12.14.

Изменяющие действия панели заданы в разделе 12.16, разрешённый просмотр файлов — в разделе 12.17. Выдача/отзыв служебного доступа и восстановление второго фактора заданы в разделах 12.18–12.19. Просмотр состояния платежа не является разрешением на ручной возврат или изменение суммы.

### 12.16. Действия администратора и финансовые ограничения

Администратор может **приостанавливать и возобновлять новые конвертации аккаунта** с обязательным указанием причины. Приостановка действует и на сайт, и на API независимо от числа устройств или замены ключа. Новые конвертации отклоняются с понятным сообщением без списания попытки; уже принятые задания продолжаются по обычным правилам.

Вход в кабинет, скачивание сохранённых результатов в пределах их сроков и управление подпиской остаются доступны. Это не удаление аккаунта и не системная остановка заданий по разделу 6.4. Поддержке право приостанавливать конвертации не предоставляется.

Администратор может **отдельно отключить пользовательский API-ключ**, не получая доступа к его значению. Отключённый ключ перестаёт авторизовать новые запросы; уже принятые задания продолжаются. Пользователь выпускает новый ключ вручную по разделу 7, после завершения текущих конвертаций. Возобновление конвертаций не включает ранее отключённый ключ автоматически.

Действия, их причина, администратор, время и результат фиксируются в журнале безопасности со сроком 90 дней по разделу 12.14.

В первой версии панель предоставляет **просмотр тарифов, платежей и возвратов**. Изменение подписки и расчёт возврата выполняются через установленные сценарии сервиса; ручного редактирования тарифов, пользовательских квот, цен и сумм возврата нет. Дополнительно администратор может повторить ту же неуспешную операцию возврата без изменения суммы по разделу 11.10; это не разрешение на произвольный новый возврат.

### 12.17. Запрос и отзыв разрешения на просмотр файлов

Сотрудник поддержки или администратор указывает причину разбора и запрашивает доступ **к конкретным сохранённым файлам пользователя**. Пользователь видит запрос в кабинете: сотрудника, причину и выбранные файлы. До подтверждения доступа к содержимому нет.

Пользователь подтверждает запрос **почтовым кодом на текущий email**. Действуют общие параметры почтовых кодов раздела 6.1 и ограничения рассылки разделов 12.12–12.13. Код и разрешение относятся к этому запросу, его сотруднику и перечню файлов, а не ко всему хранилищу пользователя.

Разрешение действует **до 24 часов от успешного подтверждения или до окончания разбора — что наступит раньше**. Пользователь может отозвать его в кабинете в любой момент; после отзыва, истечения срока или завершения разбора дальнейший доступ прекращается. Просмотр не продлевает разрешение или исходный срок хранения результата.

Проверка разрешения выполняется при каждом обращении к содержимому. Разрешение не открывает удалённые/просроченные файлы и не восстанавливает удалённый аккаунт. Запрос, подтверждение, обращения к файлам и прекращение доступа журналируются по разделу 12.14 без содержимого, исходных имён файлов и кодов.

### 12.18. Выдача и отзыв служебного доступа

Администратор приглашает сотрудника **по email с назначением роли поддержки или администратора**. Одноразовое приглашение действует **24 часа**. Сотрудник сам задаёт пароль по установленным правилам и настраивает второй фактор в приложении-аутентификаторе; служебный доступ предоставляется после завершения настройки и успешной аутентификации. Приглашение не позволяет получить права через обычную публичную регистрацию.

**При отключении сотрудника его служебные права и все служебные сессии прекращаются сразу.** Ранее выданное пользователем разрешение на просмотр файлов не позволяет отключённому сотруднику продолжать доступ. Изменение роли также применяется сервером без сохранения прежних полномочий в старом интерфейсе или сессии.

Первого администратора создают **при развёртывании** по операционной процедуре, описанной в файле технологий. Последнего действующего администратора нельзя отключить или понизить через панель; проверка учитывает фактически активные служебные учётные записи, а не только ещё не принятые приглашения.

Выдача приглашения, назначение/изменение роли, активация и отключение служебного доступа фиксируются в журнале безопасности по разделу 12.14. Секрет приглашения, пароли, коды приложения и резервные коды в журнал не включаются.

### 12.19. Восстановление второго фактора сотрудников

Сотруднику выдаются **10 одноразовых резервных кодов**, показываемых **один раз** при настройке второго фактора. Код после успешного использования больше не принимается; значения защищаются при хранении и не раскрываются администратору через панель.

При потере приложения **пароль и действующий резервный код** позволяют перейти к настройке нового второго фактора. До завершения настройки обычный доступ к служебной панели не предоставляется. После восстановления прежний фактор и старые резервные коды отключаются; выдаётся новый набор из 10 одноразовых кодов с тем же правилом однократного показа. Ранее открытые служебные сессии завершаются; дальнейший вход требует пароль и новый второй фактор.

Если утрачены и приложение, и резервные коды, служебный доступ **вручную восстанавливает владелец проекта через инфраструктуру**, по операционной процедуре файла технологий. Восстановление только по email не предоставляется. Эти правила относятся к сотрудникам; для обычного пользователя действует отдельный сценарий потери почты по разделу 6.5.

Сервер проверяет полномочия, пароль и одноразовость резервного кода; повторное использование и конкурентное применение одного кода не предоставляют дополнительный доступ. Начало и результат восстановления, замена фактора и прекращение сессий журналируются по разделу 12.14 без секретных значений.

## 13. Telegram-бот — второй этап

Бот реализуется на втором этапе и **не входит в первую версию**. Бот работает **только в личных сообщениях**, обращается к нашему API с пользовательским ключом и возвращает ZIP в тот же личный чат. Группы, каналы, сторонние сайты и оплата внутри Telegram не входят в объём этапа 2; управление подпиской остаётся на сайте.

### 13.1. Привязка и отключение

1. При первом запуске бот показывает краткую инструкцию, ссылку на кабинет и уведомление: API-ключ, исходные файлы и результаты передаются через Telegram; для конфиденциальных материалов можно использовать сайт. До отправки ключа пользователь подтверждает, что понял этот способ передачи. Это не разрешает стороннюю обработку OCR/конвертации.
2. Нужен аккаунт с подтверждённым email. Пользователь **сам создаёт API-ключ на сайте**, выбирает «Привязать ключ» в личном чате и отправляет ключ. Бот не создаёт ключ за пользователя и не запрашивает пароль или почтовые коды. Недействительный ключ отклоняется с инструкцией получить действующий в кабинете.
3. Бот проверяет ключ через API и связывает внутренний ID аккаунта с числовыми ID пользователя Telegram и личного чата. Имя/username Telegram не является идентификатором владельца. Допускается **одна активная привязка Telegram на аккаунт сервиса и один аккаунт сервиса на личный чат**. Привязка к другому Telegram-пользователю возможна после отвязки прежней на сайте или в прежнем чате; молчаливого перехвата привязки новым чатом нет.
4. Сообщение с ключом удаляется ботом сразу после получения независимо от результата проверки, если Telegram позволяет выполнить удаление. Значение не повторяется в ответах, уведомлениях, журналах и интерфейсе привязки. При невозможности удалить сообщение бот просит пользователя удалить его вручную, не цитируя ключ. Возможность удаления входящих сообщений в личном чате и ограничения задаёт [Telegram deleteMessage](https://core.telegram.org/bots/api#deletemessage); удаление сообщения не гарантирует удаления всех внутренних копий Telegram.
5. Ключ хранится в нашем окружении в зашифрованном виде, доступен только служебному процессу бота для запросов к API; администратору значение не раскрывается. Перед новым запросом и выдачей результата проверяются активность привязки и действительность ключа. Отключение/замена ключа, смена/восстановление пароля и удаление аккаунта немедленно прекращают использование прежней привязки. Уже принятые задания продолжаются по общим правилам, кроме удаления аккаунта; результаты доступны владельцу в кабинете.
6. Действие «Отвязать» доступно в чате, «Отвязать Telegram» — в кабинете этапа 2; оба требуют явного подтверждения. Привязка отключается сразу, рабочая копия ключа и черновик удаляются, новые запросы и отправка результатов в прежний чат прекращаются. Сам API-ключ не отзывается: его использование в других программах сохраняется. Уже загруженные в Telegram сообщения/архивы автоматически не очищаются; пользователь управляет историей чата в Telegram.
7. После отключения ключа пользователь вручную создаёт новый на сайте по разделу 7 и заново привязывает его в чате. Для другого аккаунта сначала выполняется отвязка текущего. Автоматической отправки старых результатов после новой привязки нет. При новой действующей привязке **того же владельца в том же исходном чате** можно вручную повторно получить ранее готовый результат бота в пределах срока хранения. Перенос старых отправок в другой чат не выполняется.

Язык бота выбирается кнопками: **украинский, русский, английский**, по умолчанию украинский. Выбор сохраняется для активной привязки и не меняет автоматически язык сайта или распознаваемого текста. Доступны действия: новая конвертация, параметры текущего набора, лимиты/тариф, повторная выдача результата, справка и отвязка.

### 13.2. Добавление файлов и запуск

- Пользователь создаёт черновик операции и добавляет файлы в порядке поступления. На базовом тарифе — один входной файл, на платном — до пяти. Альбом Telegram не запускает конвертацию автоматически; он формирует список того же черновика. Дополнительный файл сверх пакетного предела не добавляется, причина показывается; пользователь может удалить лишние и сформировать новый набор.
- Документы PDF/DOCX и изображения принимаются как файлы Telegram с проверкой реальных размера, типа и содержимого. Фотография, отправленная обычным фото, принимается в наибольшем доступном от Telegram размере как изображение JPEG; бот предупреждает, что для исходного качества нужно отправить её **как файл**. Ограничения применяются к фактически полученному изображению; восстановление потерянного при передаче качества не обещается.
- В одной операции одно направление. Смешанные JPG/JPEG/PNG/статические WEBP допустимы для изображения → PDF. Несовместимый с направлением файл показывается с причиной и не добавляется вместо другого автоматически.
- До запуска можно удалить файл, очистить черновик и кнопками переместить изображение выше/ниже в списке. Перед «Конвертировать» показываются направление, порядок, число файлов, выбранные страницы и параметры. Только явное нажатие запускает конвертацию через API.
- Без активности **30 минут** черновик истекает; пользователь получает понятное сообщение при следующем обращении. Очистка/истечение черновика не списывают попытки и не являются отменой уже принятого задания. После запуска API-задание отменить нельзя.
- На запуске API повторно проверяет действующий тариф, остатки, хранилище, параметры и очередь. При остатке две попытки и пяти файлах допускаются первые два по установленному порядку, остальные получают причину отказа. Ошибки отдельных файлов не останавливают остальные; автоматического добора или повторной отправки нет.

### 13.3. Направления и параметры

| Вход/направление | Поведение бота |
| --- | --- |
| PDF | Пользователь выбирает DOCX, JPG или WEBP перед запуском |
| DOCX | Выход PDF выбран автоматически |
| Изображения | Выход PDF выбран автоматически; «Объединить в один PDF» по умолчанию выключено |
| PDF → JPG/WEBP | По умолчанию все страницы каждого PDF; для многостраничного файла можно ввести номера/диапазоны, например `1,3-5`, отдельно для каждого PDF |
| DPI/качество PDF → изображения | Одна настройка на весь набор: 72/150/300 DPI, по умолчанию 150; качество 1–100, по умолчанию 85 |
| OCR | Автоматическое определение языков, уже подключённых на соответствующем этапе OCR: исходные шесть, после расширения — девять печатных языков по разделу 2.5. Отдельного обязательного выбора языка нет; рукописные языки ограничены своим перечнем |

До ввода страниц показывается их количество. Повторы номеров объединяются; результат формируется по возрастанию исходных номеров страниц. Пустой набор, ноль, отрицательные/несуществующие страницы и неверный диапазон отклоняются с объяснением без запуска. Для одностраничного PDF шаг выбора пропускается. В боте не требуется интерфейс миниатюр сайта.

Параметры нового черновика возвращаются к значениям по умолчанию; язык интерфейса сохраняется. A4, поля, белый фон, автоматическая ориентация, правила ошибок и подсчёт успешных исходников совпадают с сайтом/API. Объединение не увеличивает пакетный предел: на базовом тарифе оно может объединить только единственное допустимое изображение.

### 13.4. Обработка, ZIP и повторная выдача

Бот использует асинхронные задания API, сохраняет ID принятого задания и проверяет его не чаще одного раза в 5 секунд с соблюдением общего предела запросов. Пользователю показываются принятие, очередь, обработка, готовность, частичный результат или ошибка. Бот обновляет сообщение при изменении состояния, не отправляет отдельное сообщение на каждый опрос и не показывает выдуманный процент готовности.

**ZIP выдаётся по каждому успешно обработанному исходнику отдельно**, в том числе при единственном выходном файле. Если изображения объединены, отправляется один ZIP с одним PDF. Один общий ZIP всего набора не добавляется. При ошибке файла бот называет этот файл и причину в личном чате, остальные успешные результаты отправляет. Результаты сохраняются в кабинете владельца на 6 календарных месяцев; успешные исходники расходуют общие попытки сайта/API/бота.

Сбой отправки ZIP в Telegram не отменяет уже успешную конвертацию и её списание. Пользователь может вручную повторить получение готового ZIP без новой конвертации и без продления хранения. Если отправка не подтверждена, бот сообщает об этом; повторная выдача может повторно доставить тот же архив. При блокировке бота или недействительном ключе автоматической доставки нет, файлы остаются в кабинете по общим правилам.

Повторная доставка Telegram одного события, повторное нажатие «Конвертировать» для уже отправленного черновика и повторное получение ответа API не создают новое задание и не списывают попытки дважды. Для запуска сохраняется идентификатор операции, связанный с владельцем и черновиком. Если ответ о принятии потерян, бот проверяет наличие задания по этой операции **без повторной отправки исходников**; если задание не найдено, предлагает пользователю вручную сформировать новую отправку. Один идентификатор не может обозначать другое содержимое. Технические записи защиты от повторов хранятся 30 дней без ключей, исходных имён и содержимого файлов.

Отвязка/недействительность ключа проверяются также перед выдачей ZIP. Старые задания не отправляются другому владельцу/чату после перепривязки. Уже начатую передачу или уже полученный в Telegram архив технически нельзя считать отозванным; в кабинете доступ прекращается согласно общим правилам удаления.

### 13.5. Ограничения передачи и служебные данные

Бот должен поддерживать **полные установленные размеры своего тарифа**, включая входные документы максимального тарифа до 100 МБ, изображения до 50 МБ и ZIP из допустимого результата до 500 МБ плюс служебные данные архива. Перед запуском проверяется возможность передачи; нельзя списать попытку за отказ передачи до конвертации, незаметно уменьшить тарифный размер, разбить результат на иные форматы или заменить обещанный ZIP только ссылкой на сайт.

Облачный Bot API ограничивает скачивание через `getFile` размером 20 МБ, загрузку нового документа через `sendDocument` — 50 МБ. Документация локального Bot API описывает скачивание без такого лимита и загрузку до 2000 МБ. Следовательно, **обычного облачного режима недостаточно для полного объёма этапа 2**. Совместимый способ подключения и его развёртывание выбираются в отдельном файле технологий до реализации бота; этим ТЗ конкретный режим/инфраструктура не назначаются. Источники: [getFile](https://core.telegram.org/bots/api#getfile), [sendDocument](https://core.telegram.org/bots/api#senddocument), [локальный Bot API](https://core.telegram.org/bots/api#using-a-local-bot-api-server). Перед интеграцией ограничения платформы проверяются повторно.

Локальные копии исходников бота удаляются сразу после надёжной передачи в API, ошибки, удаления файла из черновика или истечения черновика, максимум за 15 минут от события. Если для выбора страниц исходник уже передан в API как подготовительный файл, он остаётся доступен только владельцу/черновику до запуска либо истечения 30 минут без активности. После принятия конвертации действует хранение временных исходников очереди по разделу 10.4. Подготовительные файлы не попадают в кабинет и не расходуют квоту успешных конвертаций.

Временный ZIP на стороне бота удаляется сразу после завершения/ошибки отправки в Telegram, максимум за 15 минут; копия ZIP на стороне API очищается после его выдачи боту по разделу 10.2. В резервные копии исходники, черновики с файлами и ZIP не включаются. После сбоя очистка осиротевших временных данных выполняется в течение часа от восстановления. Привязка и ключ удаляются из рабочего хранилища сразу при отвязке/отключении; старые копии подчиняются сроку 30 дней и механизму запрета восстановления отозванного доступа по разделу 10.5. Журналы — по разделу 12.14, без текста сообщений, ключей и содержимого документов.

Сроки очистки нашего сервиса **не являются обещанием удаления данных на серверах Telegram**. Передача через Telegram и хранение истории чата раскрываются в уведомлении до привязки и первой отправки файлов; пользователь может выбирать сайт. Собственная серверная обработка, хранение и копии сервиса по-прежнему располагаются в ЕС.

| Область | Основные проверки |

Отключение сразу прекращает служебные права/сессии, в том числе доступ по ещё не истёкшему разрешению на файлы. Последнего активного администратора нельзя отключить/понизить через панель |

Повторное применение кода отклоняется. При полной утрате — ручное восстановление владельцем через инфраструктуру, без email-only обхода |
| Обязательные технические механизмы | Серверные проверки и резерв квот без двойного списания; одноразовые коды с привязкой к операции; защищённые непредсказуемые API-ключи в заголовке; безопасные машинные ошибки/имена результатов/очистка ZIP; подтверждение очистки и владелец при удалении; серверная проверка платежей без двойной активации/списания/возврата; изоляция обработки и защита сессий/паролей |
| Действия администратора | Приостановка/возобновление новых конвертаций с причиной действует на сайт/API; принятые задания продолжаются, кабинет/скачивание/подписка доступны. | Изменения в льготные сутки | Выключение автопродления/отмена прекращают повторы и сразу дают базовый тариф, без долга или возврата за неоплаченные часы. Для смены сначала оплачивается текущее продление либо оно отменяется и оформляется новая покупка; неоплаченные часы не дают денежного зачёта |
| Возврат после удаления | Удаление не создаёт возврат за оплаченный остаток. Если остаётся ранее возникший возврат либо возвращается ошибочное/устаревшее списание, статусы отправляются на последний подтверждённый email без восстановления аккаунта. Контактная запись только для этой операции, до успешного завершения и ещё не более 30 дней; при отсутствии возврата запись не создаётся |
| Платёжные переходы | Pro ↔ максимальный при прежнем типе оплаты сохраняет конец периода, перерасчёт только за остаток. Месяц ↔ год начинает новый полный период и однократно засчитывает старый остаток; доплата/возврат разницы на карту. История всех оплат/доплат/возвратов исключает повторный зачёт; пример Pro €5 → повышение в середине с доплатой €2,50 → немедленная отмена даёт возврат €5 |
| Календарь подписки | Первый период от активации после успешной оплаты; календарный месяц/год, время UTC. При отсутствии числа используется конец месяца с сохранением исходного числа для следующих периодов; проверяются 31-е число и високосные годы |
| Точность и деньги | Перерасчёт по фактическим секундам периода, годовые цены €51/€102 со скидкой. Округление только итоговой доплаты/возврата до евроцента: половина цента вверх, промежуточные значения не округляются |
| Конечные цены и пробный доступ | Pro €5/€51, максимальный €10/€102 — конечные цены сервиса с применимыми налогами, без обязательных сборов сверх прайса. Бесплатного пробного периода платных тарифов нет; базовый тариф остаётся бесплатным |
| Enterprise и платёжные параметры | Enterprise в первой версии: договорная цена и обращение по email без покупки/активации особого тарифа. Будущая команда: один мастер плюс до 10 дополнительных аккаунтов, Детальные правила командного тарифа находятся за пределами первой версии. Собственного денежного минимума нет; ниже технического минимума доплата не выполняет переход, возврат сохраняется к урегулированию. Продавец — Украина, инфраструктура остаётся в ЕС |
| Малые суммы | На условном техническом минимуме €0,50 доплата €0,01 не увеличивается до €0,50 и не меняет тариф; возврат €0,01 не сгорает и передаётся поддержке без отката отмены/понижения. Денежный статус не становится успешным без исполнения, удаление аккаунта не списывает ранее возникшее обязательство. €0,00 после округления не создаёт денежную операцию |
| Потеря почты | 10 резервных кодов, однократный показ, защищённое хранение, отзыв старого набора при замене. Код и подтверждение нового свободного email позволяют задать новый пароль; один код не завершает два восстановления. Старые сессии/ключ/привязка бота отключены, подписка/файлы/квоты сохранены; обычная смена почты по-прежнему требует два почтовых подтверждения. Без резервного кода — поддержка, один чек не достаточен, восстановление не гарантировано |
| Финансовые сведения ФОП | Минимальный реестр операций без полных карточных данных, паролей и файлов пользователя хранится отдельно от профиля. Категория, начало отсчёта и продления определяют обязательный срок; нет универсального удаления через 3 года от платежа. Удаление аккаунта не стирает обязательные записи и не сохраняет пользовательские файлы |
| Удаление аккаунта | Без кода ничего не удаляется; с кодом доступ/сессии/ключ отключаются сразу, очередь удаляется, активные конвертации системно останавливаются и не публикуют результат. Аккаунт/файлы удаляются, подписка и списания прекращаются; возврат за оставшийся оплаченный срок не создаётся, пользователь предупреждён до подтверждения |
| Принятые задания | Смена пароля не отменяет API-обработку; заполнение хранилища не отменяет принятый пакет; новые операции подчиняются запретам. Удаление аккаунта — специальное исключение с удалением очереди и системной остановкой обработки |

Проверяются сроки удаления временных копий и ZIP, истечение черновика, невосстановление отозванной привязки из копии; сроки нашего сервиса не обещают очистку серверов Telegram |

Отсутствие бота и дополнений API из раздела 9.5 не является дефектом этапа 1.

**Отдельная приёмка расширений OCR:** испанский, итальянский и португальский проверяются по дополненному контрольному набору печатного текста с автоопределением и смешанными документами. Рукопись проверяется отдельно на украинском/русском/английском, включая сочетание с печатным текстом; до её приёмки утверждаются образцы, эталонные расшифровки и отдельные критерии качества. Отсутствие этих расширений не является дефектом первой версии.

## 15. Дальнейшие работы

### 15.1. Enterprise

В первой версии Enterprise представлен карточкой с договорной ценой и обращением по email. Реализация индивидуального тарифа и управления командой относится к отдельному будущему этапу.

Команда включает **один мастер-аккаунт и максимум 10 дополнительных аккаунтов**, всего не более **11 аккаунтов**. Мастер-аккаунт подключает дополнительные аккаунты к своей команде.

Общие и раздельные квоты, хранилище, API-ключи, доступ к файлам, роли участников, подключение и отключение аккаунтов, цена и оплата определяются отдельным ТЗ на командный тариф. До его реализации действуют фиксированные тарифы и изоляция аккаунтов. Членство в будущей команде само по себе не предоставляет общий доступ к файлам, единый API-ключ или безлимит.

### 15.2. Подготовка к разработке и приёмке

К следующим работам необходимо вернуться отдельно:

1. Актуализировать [technology-stack.md](./technology-stack.md): технологии, обработку/OCR, платёжный и почтовый провайдеры, инфраструктуру, транспорт Telegram и развёртывание — в соответствии с настоящим ТЗ.
2. Подготовить технический контракт API: адреса, методы, поля, заголовки, схемы запросов/ответов и ошибок по разделу 9.4.
3. Подготовить и утвердить контрольные документы, эталонные результаты и сценарии проверки конвертации/OCR и нагрузки по разделам 2.3–2.5 и 12.8 до приёмки соответствующего этапа.
