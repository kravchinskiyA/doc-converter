# План проверки конвертации PDF → DOCX и OCR

**Дата:** 28 октября 2026 г.  
**Статус:** проект процедуры испытаний; прогоны ещё не выполнялись.

Основание — [ТЗ 1.36](./technical-specification-final.md), §§2.3–2.4, 3.4–3.7, 12.8, и [технологический стек](./technology-stack.md), §5. Требования ТЗ сохраняют свой статус; конкретная организация стенда ниже — техническое предложение.

## 1. Что проверяем

Для PDF → DOCX со сканами и таблицами пользователь выбрал PaddleOCR / PP-StructureV3. Выбор движка закрыт; качество и ограничения ещё не проверены. Оценивается весь путь от исходного PDF до одного редактируемого DOCX. Промежуточный текст OCR или успешное создание файла сами по себе не подтверждают качество результата.

Sharp/libvips, pdf-lib, PDFium и LibreOffice уже утверждены для своих направлений. Их техническая проверка также нужна; повторного согласования самого выбора не требуется.

## 2. Контрольные документы и эталоны

Контрольных документов пользователя пока нет. По ТЗ набор готовит разработчик, а пользователь утверждает его перед приёмкой. Для первоначального сравнения можно подготовить синтетические документы из исходного текста и известных таблиц; они не заменяют дальнейшую проверку реалистичных макетов и сканов.

| Группа | Содержимое | Что сохраняется как эталон |
| --- | --- | --- |
| Одноязычные документы | Печатный текст отдельно на русском, украинском, английском, французском, немецком и польском | Полный текст, порядок абзацев, заголовки и списки |
| Смешанные языки | Несколько согласованных языков на одной странице и на разных страницах, включая кириллицу и латиницу | Текст каждого блока и его место в документе |
| Числа | Даты, суммы, десятичные разделители, отрицательные значения, проценты, номера с ведущими нулями | Точные значения и местоположение контрольных полей |
| Простые таблицы | Строки, столбцы, заголовки, числа и текст в ячейках | Структура таблицы и содержимое каждой ячейки |
| Сложные примеры | Объединённые ячейки, перенос таблицы между страницами, несколько колонок, формулы | Отдельно согласуемый ожидаемый результат по ТЗ §2.4 |
| Макет и изображения | Многостраничные документы с абзацами, списками, иллюстрациями | Состав содержимого и порядок чтения |

Подготовить PDF с текстовым слоем и чёткие растровые сканы с известным исходным текстом. Для проверки OCR убедиться, что в сканах нет скрытого текстового слоя. Добавить отдельно повёрнутые/нечёткие сканы: критерии чёткого скана к ним автоматически не применять.

Для каждого файла записать идентификатор, источник, контрольную сумму, языки, число страниц и ожидаемые результаты. Эталонную расшифровку проверить вручную; она не должна создаваться тем же OCR, который испытывается.

## 3. Пробный стенд

Техническое предложение — небольшой автономный стенд в нашем окружении в ЕС, без готового сайта, регистрации и оплаты. Он принимает контрольный PDF, выполняет полный конвейер и сохраняет DOCX и отчёт. Пользовательские документы внешним сервисам не передаются.

Зафиксировать версии программ, конфигурацию, модели и их контрольные суммы, используемые шрифты, параметры машины. Модели установить до прогона; обработка файлов не должна зависеть от внешнего API. Окружение воспроизводимо, условия одинаковы для сравниваемых кандидатов. Пользователь подтвердил отдельные рабочие процессы и допустимость Python для OCR; для первой проверки PP-StructureV3 предлагается Python-интеграция. Конкретный способ изоляции ещё нужно выбрать. Возможность рабочего конвейера без Python рассматривается отдельно в технологическом стеке, §5.6, и не считается проверенной.

По ТЗ отдельно контролируются все процессы одной задачи: OCR, анализ макета, рендеринг, сборка и проверка результата. Лимит памяти 2 ГБ относится ко всей задаче, а не к каждому дочернему процессу. Активная обработка ограничена 10 минутами; загрузка/ожидание очереди/скачивание учитываются отдельно.

## 4. Как оценивать результат

1. **Открытие и редактируемость:** DOCX открывается, текст можно редактировать, таблицы представлены редактируемыми ячейками; страницы не подменены целиком картинками.
2. **Текст:** извлечь текст из итогового DOCX, сравнить с эталоном, сохранить различия. Для чётких контрольных сканов считать CER отдельно на документ: `(замены + пропуски + вставки) / число символов эталона × 100%`, исключив пробелы и переносы по ТЗ. Порог — не более 2% на каждый утверждённый контрольный документ; усреднение между документами не заменяет проверку каждого.
3. **Цифры:** отдельно сверить значения контрольных полей с эталоном. Показывать каждую подмену/пропуск, включая знак, разделитель и ведущие нули. Общий CER не заменяет проверки числовых данных, важных пользователю.
4. **Таблицы:** сравнить строки, столбцы, связи объединённых ячеек и размещение текста/чисел по ячейкам. Проверить, что данные не перепутаны между строками и колонками и таблица не стала изображением. Сложные случаи оценивать по отдельно утверждённым примерам.
5. **Полнота и оформление:** проверить отсутствие потерянных страниц, абзацев и изображений; порядок чтения, заголовки и списки. Открыть DOCX и визуально сравнить с оригиналом. Похожие шрифты, небольшие сдвиги и изменения переносов оценивать по допускам ТЗ §2.4. Точность текста проверять непосредственно по DOCX, а не только по его визуальному представлению.
6. **Языки:** проходить те же файлы без ручного выбора языка пользователем. Успех с заранее заданным языком не доказывает автоматическое определение и поддержку смешанного документа.
7. **Ресурсы:** измерить полное время активной обработки и пиковую память всей группы процессов. Проверить размер готового результата и установленные ограничения изображений. Повторить на нескольких задачах одновременно; итоговая проверка общей нагрузки — до 5 активных задач по актуальному ТЗ.

Отдельные прогоны — повреждённый/защищённый PDF, превышение времени/памяти/объёма. Ожидаются контролируемая ошибка и очистка временных данных; частичный DOCX не выдаётся за полный успешный результат. Не устанавливать автоматическое принятие по одному высокому показателю уверенности OCR.

## 5. Отчёт и решение

Для каждого контрольного файла отчёт содержит версию/конфигурацию движка, результат открытия и редактируемости, CER с различиями текста, ошибки числовых полей, ошибки структуры таблиц, потерянные элементы, время, пиковую память и ссылки на выходной DOCX и материалы сравнения. Каждый пункт получает статус «пройден», «не пройден» либо «не проверен» с причиной.

Успех небольшого синтетического набора даёт основание продолжить испытания, но не означает выполнения приёмки для всех документов. Если PP-StructureV3 не проходит критерии, зафиксировать точные причины и сравнить другой локальный конвейер на тех же эталонах. Tesseract можно использовать для сравнения распознанного текста; без отдельного восстановления структуры он не считается заменой всего PDF → DOCX. Для pdf2docx сначала проверить зависимости и условия их использования.

Итоговый выбор PDF → DOCX/OCR фиксируется после проверки на утверждённом наборе и оценки сборок/моделей. Подготовленный план не является отчётом об успешных испытаниях.
