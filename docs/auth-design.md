# Авторизация для Next.js и NestJS

**Дата:** 28 октября 2026 г.  
**Статус:** Better Auth в NestJS, адаптер Prisma, серверные сессии PostgreSQL без кеша в cookie, один публичный origin и сроки сессий по §2.1 утверждены пользователем. Остальные настройки и интеграция требуют проработки; установка, прототип и испытания не выполнены.  
**Основание:** [ТЗ 1.36](./technical-specification-final.md), §§4, 6–7, 10.5, 12.12–12.19; выбранные NestJS, Next.js, PostgreSQL и Prisma.

## 1. Утверждённый вариант

**Better Auth в NestJS + адаптер Prisma + серверные сессии в PostgreSQL.** Next.js отображает формы и получает состояние входа от NestJS. Один серверный модуль управляет учётными данными и сессиями; второго независимого сервера авторизации в Next.js не создаётся. Better Auth работает в нашем окружении в ЕС, отдельный облачный сервис авторизации для этой схемы не требуется.

Better Auth предоставляет основу email/пароль, сессий, почтовых OTP и TOTP. Для PostgreSQL есть [адаптер Prisma](https://better-auth.com/docs/adapters/prisma). Однако это не готовая реализация всех сценариев нашего ТЗ: операции аккаунта и контроль полномочий потребуют собственного кода в NestJS и, где необходимо, расширений Better Auth.

Для первой версии пользователь выбрал Better Auth, чтобы использовать готовую основу сессий и факторов входа. Рассмотренная альтернатива — модуль NestJS с [Passport](https://docs.nestjs.com/recipes/passport) и отдельной реализацией сессий/операций аккаунта — в выбранный стек не входит. Правила кодов, восстановления и служебного доступа остаются задачей проекта.

## 2. Взаимодействие сайта и backend

Утверждён один публичный origin — будущий HTTPS-домен сайта. Зона `.ua` выбрана пользователем; полное доменное имя и регистрация не подтверждены. На уровне входного прокси страницы направляются в Next.js, маршруты API/авторизации — в NestJS. Точные префиксы маршрутов закрепляются при реализации; они не должны пересекаться с маршрутами самого Next.js.

- Браузер обращается к NestJS через адреса API того же origin; файлы по утверждённому решению принимает и выдаёт NestJS.
- Cookie содержит непрозрачный секретный идентификатор сессии; состояние входа хранится в PostgreSQL через Prisma. Предлагаются `HttpOnly`, `Secure`, `SameSite=Lax`, область одного хоста без общего `Domain`; конкретное имя и `Path` ещё не закреплены. Значение cookie и заголовки авторизации не записываются в журналы.
- Для немедленного отзыва утверждена проверка сессии по PostgreSQL без кеша: `session.cookieCache` отключается, Redis как второе хранилище сессий не подключается. Каждый защищённый запрос NestJS проверяет сессию, состояние аккаунта и актуальные полномочия на сервере. При недоступной проверке доступ не предоставляется. Redis остаётся выбранным хранилищем очереди.
- Изменяющие запросы защищаются от CSRF: проверяется разрешённый origin, применяется подходящая защита запросов с cookie. Сохраняются защитные проверки Better Auth; собственные маршруты NestJS должны обеспечивать такую же защиту. Одного `SameSite` недостаточно для всех сценариев.
- При серверном отображении Next.js передаёт cookie только доверенному NestJS и запрашивает актуальное состояние. Ответы с персональными данными и `Set-Cookie` не попадают в общий кеш. Если операция выполняется через сервер Next.js, передача новых/удалённых cookie браузеру должна быть предусмотрена явно; проверка интерфейса не заменяет проверки NestJS.
- Гостевой идентификатор и пользовательская сессия имеют разные назначения. Гостевой cookie и серверные квоты сохраняют правила ТЗ §4.2; использование плагина анонимных аккаунтов не считается выбранным решением.

Основание для механизма и отказа от кеша сессии — [Better Auth: Session Management](https://better-auth.com/docs/concepts/session-management); для cookie и защиты сессий — [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html). Конкретные сроки не заданы исходным ТЗ и утверждены пользователем в §2.1 этого документа; значения библиотеки по умолчанию их не заменяют.

### 2.1. Утверждённые сроки сессий

**Статус: сроки и политика продления утверждены пользователем.** Значения — согласованный выбор для этого проекта, а не численные требования OWASP или исходного ТЗ.

| Вид доступа | Завершение после бездействия | Максимальный срок после успешного входа | Повторный вход |
| --- | --- | --- | --- |
| Пользовательский, включая неподтверждённый аккаунт | 7 суток | 30 суток | Email и пароль |
| Служебный: поддержка и администратор | 15 минут | 8 часов | Email, пароль и TOTP приложения |

Сутки здесь равны 24 часам. У каждой сессии свои сроки; активность на другом устройстве её не продлевает. Вход пользователя сохраняется между посещениями в пределах этих сроков, чтобы не требовать пароль при каждом возвращении. Для служебного доступа выбран более короткий период из-за полномочий сотрудника.

Правила утверждённой политики:

1. Действует более ранний из двух сроков: `последняя учитываемая активность + период бездействия` либо `момент успешного входа + максимальный срок`. После истечения даже запрос активности не оживляет сессию; необходим повторный вход. Плановое обновление cookie или замена идентификатора не начинают максимальный срок заново.
2. Учитываются действия пользователя, дошедшие до сервера: например, открытие защищённой страницы, отправка формы, запуск загрузки или скачивания. Автоматический опрос состояния задания/сессии, обновление вкладки по таймеру и действия worker не продлевают вход. Точный перечень маршрутов активности закрепляется в контракте; одного клиентского заявления об активности недостаточно.
3. Служебный срок начинается после успешной проверки пароля и TOTP. Работа в обычном пользовательском кабинете не продлевает служебный доступ. Способ разделения контекстов и учёт времени проверяются в прототипе; обычная пользовательская сессия сама по себе не даёт служебных прав.
4. Сроки проверяет NestJS по серверному времени перед предоставлением доступа; интерфейс может предупредить о завершении, но не управляет действительностью сессии. Закрытие браузера не заменяет серверный контроль срока, явный выход отзывает сессию на сервере.
5. Истечение сессии само по себе не отключает отдельный API-ключ и не отменяет уже принятые задания; для дальнейшего доступа через сайт нужен повторный вход. Уже согласованные правила смены/восстановления данных, удаления аккаунта и отзыва сотрудника продолжают завершать доступ немедленно, не дожидаясь тайм-аута. Гостевой идентификатор, квоты и сроки хранения файлов этой политикой не изменяются.

OWASP [разделяет срок бездействия и абсолютный срок](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#session-expiration) и требует проверять их на сервере. Better Auth документирует скользящее продление через `expiresIn`/`updateAge`; одна такая настройка не доказывает соблюдение обоих пределов и разных правил пользователей/сотрудников. Понадобятся серверные проверки времени успешного входа и последней учитываемой активности, согласованные с истечением записи Better Auth и cookie. Физическая схема, частота записи активности и механизм продления ещё не закреплены.

В прототипе дополнительно проверяются оба срока на границе, запрет продления фоновым опросом, независимость устройств и служебного контекста, отсутствие оживления при конкурентных запросах и сохранение максимального срока при обновлении идентификатора. Это план испытаний; проверки не выполнялись.

## 3. Соответствие сценариям ТЗ

| Область | Что требуется реализовать и проверить |
| --- | --- |
| Регистрация и неподтверждённый аккаунт | Email/пароль без обязательного имени. Одинаковый ответ для нового/занятого email и разные письма по §6.1. Перенос гостевого расхода; общий расход неподтверждённого аккаунта во всех браузерах; полные 5/5 после подтверждения. Нельзя глобально запретить любой вход до подтверждения, поскольку ТЗ предусматривает использование неподтверждённого аккаунта по гостевым правилам. Доступ к кабинету, оплате и API проверяется отдельно |
| Пароли | Предлагается встроенное хеширование Better Auth через `scrypt`; параметры и допустимая нагрузка проверяются на выбранной версии. Длина 8–128, Unicode/пробелы/вставка без обрезания. Отклонение распространённых/скомпрометированных паролей обязательно; источник списка и способ проверки ещё не выбраны |
| Почтовые коды | Плагин Email OTP — основа, а не замена состояния операции. 6 цифр, 600 секунд, максимум 5 попыток, отправка не чаще минуты; общие 5 писем/час и 20/сутки на email плюс пределы IP. Код привязан к аккаунту, конкретной операции и адресам, используется однократно. Предлагается необратимое проверочное значение с серверным секретом для коротких кодов; секрет хранится отдельно, готовая конфигурация ещё не проверена |
| Смена email | Последовательное подтверждение старой и новой почты, общий срок 20 минут от первого письма без продления. Изменение адреса отменяет прежние подтверждения; доступность проверяется повторно при завершении. Выбор завершения всех сессий/отключения ключа включён по умолчанию и применяется только при успехе. Возможности Email OTP нужно дополнить состоянием всей операции по §6.2 |
| Смена/сброс пароля | Обязателен код на текущую почту. При успехе завершаются все сессии, включая текущую, и отключается API-ключ. Обычный вызов библиотеки с `revokeOtherSessions` не доказывает соблюдение этого правила; отдельно проверяются текущая сессия, ключ и отсутствие автоматического входа. Принятые конвертации продолжаются |
| Потеря почты | Отдельный сценарий §6.5: 10 кодов с однократным показом и необратимым хранением; новый свободный email, его код и новый пароль; срок 20 минут. Только успех совместно меняет учётные данные и отзывает сессии, ключ, прежний набор кодов, незавершённые операции и привязку бота. Параллельные запросы с одним кодом не дают два успеха. Коды пользовательского восстановления не подменяются кодами плагина TOTP |
| API-ключ | Отдельный модуль NestJS: один ключ, ручной выпуск, запрет выпуска/замены при текущих конвертациях, код для замены, немедленный отзыв. Для повторного показа ключа владельцу требуется защищённое обратимое хранение полного значения; одно необратимое хеширование этого требования не выполняет. Средство управления ключами ещё не выбрано |
| Сотрудники | TOTP из приложения обязателен до выдачи служебного доступа; актуальные роль и состояние проверяются при каждом запросе. Приглашения 24 часа, публичная регистрация не назначает роль. Вход по одному почтовому коду и функция доверенного устройства не должны обходить обязательный второй фактор. Разрешение пользователя на конкретные файлы проверяется отдельно от роли |
| Восстановление TOTP | Пароль и один из 10 служебных резервных кодов разрешают только настройку нового фактора. Полный доступ не выдаётся до её завершения; старый фактор, набор кодов и служебные сессии отзываются. Стандартное использование резервного кода плагина для обычного входа не считается реализацией §12.19. Пользовательские и служебные наборы разделены |
| Удаление, отзыв и резервные копии | Удаление по коду сразу прекращает доступ и сессии, отключает ключ, останавливает задания по ТЗ. Операции изменения данных и отзывов согласуются без частично успешного состояния. Использованные коды и отозванные права не оживают после восстановления копии; независимый от отката механизм отзывов остаётся инфраструктурной задачей |

Возможности библиотек: [email/пароль](https://better-auth.com/docs/authentication/email-password), [Email OTP](https://better-auth.com/docs/plugins/email-otp), [TOTP и резервные коды](https://better-auth.com/docs/plugins/2fa). Настройки защиты от перебора и рассылки проверяются по ТЗ, включая общие счётчики нескольких процессов; стандартные ограничения библиотеки не подменяют согласованные значения.

Почтовые OTP, пароли, пользовательские резервные коды, служебные коды и API-ключ имеют разные требования к хранению. Общее шифрование диска не заменяет хеширование паролей/пользовательских резервных кодов. Секрет TOTP должен оставаться доступным проверяющему компоненту в защищённом виде; конкретная схема шифрования и ротации ещё не закреплена.

## 4. Ограничения интеграции и проверка перед реализацией

В [официальном руководстве Better Auth для NestJS](https://better-auth.com/docs/integrations/nestjs) используется **поддерживаемый сообществом** `@thallesp/nestjs-better-auth`; поддержка Fastify там отмечена как beta. Выбор Better Auth не означает автоматического выбора этого пакета. Для NestJS пользователь утвердил Express. Пакет интеграции и совместимые версии проверяются в прототипе.

Прототип должен проверить:

1. Подключение к NestJS/Express и Prisma; корректную обработку тела auth-запросов без нарушения потокового multipart и будущей проверки исходного тела платёжных уведомлений. Миграции проходят принятый процесс Prisma, а не запускаются двумя независимыми средствами.
2. Изоляцию публичных маршрутов: несогласованные стандартные endpoints не дают обойти почтовое подтверждение операции, восстановление, лимиты или служебный TOTP. Серверные вызовы библиотеки также проходят проектные проверки; одного отключения пути на прокси недостаточно.
3. Атомарность завершения операций: изменения учётных данных, расход одноразового кода и отзыв сессий/ключа/привязки согласованы при гонках и сбоях. Не предполагается, что последовательность «вызвать библиотеку, затем отдельный Prisma-запрос» сама является одной транзакцией. Возможность общей транзакции или другого доказуемого механизма согласования требует проверки конкретного адаптера/расширения.
4. Немедленный отзыв на другом устройстве, запрет служебного доступа до TOTP и после отключения сотрудника, восстановление фактора без промежуточного полного входа. Конкурентное использование кодов, занятый email при завершении, ошибки писем и отсутствие секретов в журналах.
5. Сохранение гостевых/неподтверждённых квот, отсутствие выдачи новой квоты при восстановлении, доступ к файлам строго владельцу или по действующему служебному разрешению, отсутствие персональных данных в общем кеше Next.js.

Это план проверки; прототип не создан и соответствие ещё не доказано. Если интеграция не позволяет выполнить обязательные сценарии без обходов, выбор реализации пересматривается с пользователем, а требования ТЗ сохраняются.
