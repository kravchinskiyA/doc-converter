# Шифрование, ключи и секреты

**Дата:** 28 октября 2026 г.  
**Статус:** AWS KMS + Secrets Manager в ЕС, SSE-KMS и разделение способов защиты данных утверждены пользователем. Настройка и испытания не выполнялись. Основание — [ТЗ 1.36](./technical-specification-final.md), §§6–7, 10.5, 12.1, 12.5.

## 1. Утверждённая основа

**AWS KMS + AWS Secrets Manager в ЕС**, с разграничением прав приложения, отправки почты, обработчиков и служебных действий. Выбранная схема учитывает S3 и SES, но не выбирает AWS хостингом приложения: вопрос размещения пользователь пропустил в текущем согласовании.

AWS KMS управляет ключами шифрования, AWS Secrets Manager хранит секреты конфигурации. Пароли и одноразовые резервные коды пользователя имеют необратимое хранение, а повторно показываемый API-ключ и секрет TOTP требуют другого механизма. Один способ защиты не назначается всем данным.

## 2. Разделение данных

| Данные | Схема защиты | Условия реализации |
| --- | --- | --- |
| Объекты S3: результаты и временные исходники очереди | SSE-KMS с управляемым нами ключом KMS в том же регионе ЕС, что и bucket. Права на расшифровку выдаются нужным компонентам | Политики доступа, загрузка/выдача и очистка. Шифрование не делает объект публичным и не заменяет проверку владельца |
| Секреты конфигурации | Secrets Manager: учётные данные БД, серверные секреты Better Auth, секреты Stripe и служебные секреты отправки при необходимости | Получение приложением начальных прав, ротация и хранение прежних версий. Способ выдачи прав зависит от окружения и пока не назначен |
| API-ключ, полный текст которого владелец может посмотреть повторно | Шифротекст в PostgreSQL; для собственного модуля предлагается AES-256-GCM через node:crypto с ключом данных, защищённым KMS. Записи связываются с владельцем/назначением; выдача полного значения только через проверенный NestJS | Формат записи, уникальность nonce для каждого шифрования одним ключом, проверка тега, права на расшифровку, ротация и атомарный отзыв. Ключ каждого пользователя не предлагается хранить отдельным секретом конфигурации в Secrets Manager |
| Секрет TOTP | Штатная схема шифрования выбранной версии Better Auth; её серверный секрет хранится через Secrets Manager | Совместимость с политикой ключей, ротацией и восстановлением. Совпадение с собственной схемой API-ключей не предполагается; неподтверждённая замена внутреннего шифрования плагина не назначается |
| Пароли | Хеширование с солью; текущий кандидат — встроенный scrypt Better Auth | Параметры, нагрузка, Unicode и проверка слабых/скомпрометированных паролей. Обратимое шифрование паролей не используется |
| Резервные коды пользователя и почтовые коды | Необратимые проверочные значения. Для короткого почтового кода — предлагаемый HMAC с отдельным серверным секретом и привязкой к операции, плюс срок и предел попыток по ТЗ | Одноразовость, конкурентные запросы, отзыв и защита от повторного появления после отката БД. Для служебных резервных кодов отдельно проверяется интеграция TOTP |
| PostgreSQL, Redis с чувствительными данными, временные диски, распакованные файлы, ZIP и копии | Шифрование соответствующего хранилища/тома; ключи вне самого защищаемого набора данных | Конкретное средство зависит от пропущенного сейчас решения о размещении. KMS/Secrets Manager и SSE-KMS сами по себе не шифруют произвольный диск или всю БД |

Источники: [S3 SSE-KMS](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingKMSEncryption.html), [шифрование Secrets Manager](https://docs.aws.amazon.com/secretsmanager/latest/userguide/security-encryption.html), [ключи данных KMS](https://docs.aws.amazon.com/kms/latest/APIReference/API_GenerateDataKey.html), [node:crypto](https://nodejs.org/api/crypto.html). Таблица описывает утверждённую схему применения средств; инфраструктура ещё не настроена.

## 3. Как защищается ключ приложения

Для собственного шифрования API-ключа предлагается схема с отдельным ключом данных: KMS выдаёт случайный ключ и его зашифрованную копию, приложение шифрует значение локально, в БД остаются шифротекст и защищённый ключ данных. Открытый ключ данных используется только на время операции; схема не требует отправлять содержимое документов в KMS. Окончательный формат и реализация требуют проверки. Само шифрование файла S3 выполняет S3 по SSE-KMS.

Корневой ключ KMS не хранится в таблице рядом с данными и не включается в обычную копию БД. Доступ к KMS/Secrets Manager выдаётся по назначению: конвертер не получает секрет Stripe, БД аккаунтов или возможность показать пользовательский API-ключ. Имена объектов, секретов, теги и контекст шифрования содержат внутренние идентификаторы, без содержимого документов, кодов, ключей и исходных имён файлов.

## 4. Ротация и восстановление

- Период ротации и число ключей пока не назначаются. Ротация ключа шифрования не равна замене пользовательского API-ключа и сама по себе не меняет его публичное значение.
- Старый ключ нельзя уничтожать, пока остаются разрешённые к хранению данные или копии, требующие его для расшифровки. Замена ключа не переносит автоматически все существующие шифротексты на новый ключ.
- При недоступности ключа защищённая операция завершается ошибкой; запись/выдача незашифрованной копии как обход не допускается. Повреждённый шифротекст или неверный тег не выдаются пользователю как достоверное значение.
- Сохранение доступа к разрешённым резервным копиям и применение отзывов/удалений после восстановления остаются требованиями ТЗ. Выбор средств резервирования и эксплуатации пользователь сейчас пропустил; этот документ не назначает их реализацию.
- Перед использованием проверяются минимальные права, расшифровка после ротации, отказ KMS/Secrets Manager, отсутствие секретов в журналах и невозможность доступа конвертера к чужим секретам. Проверки ещё не выполнены.
